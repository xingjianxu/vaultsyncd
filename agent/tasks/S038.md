## 1. 接口决定

- **创建与移动共用一条提交路径**：`commit_namespace(gate, store, log, ns, at, &NamespaceRequest)`，`NamespaceRequest` 只有 `CreateDirectory`/`Move` 两个变体；内部统一走“请求形状 → Root 串行化 → epoch → 条目与父目录基线 → 源/目标现场 → `prepared` 意图 → 动作与复核 → `published` → 元数据事务 → ACK”。这就是卡里要求的“同一意图/恢复机制”：两者共用阶段机、证据编码与恢复顺序，差别只在证据形态（新建 before 是 `{"present":false}`，移动 before 记源位置与 inode）。
- **`EntryId` 不随路径变、移动不搬内容**：`commit_move` 从基线取身份写进意图与事务；`NamespaceWrite` 里**没有内容字段**，`NamespacePort` 里**没有内容方法**（只有 `inspect`/`create_directory`/`rename`），因此“移动只改父关系、内容流量为零”是结构性的，测试再断言内容版本引用前后一致、轨迹里没有发布/对象调用。
- **移动要能证明“同一次改名”**：意图 before 记录源 inode；`rename` 之后复核“目标同 inode + 源位置已空”，不符就给 `applied_state_mismatch` 并停在 `prepared`（不推进阶段、不写事务）。恢复的 `Complete` 同样要求目标 inode 等于 before，避免把别人放的目录当成自己移过去的。
- **动磁盘前的四类拒绝**：目录环（`to.path` 在自己子树里、`to.parent == entry`）、目标被占（`target_occupied`）、目标祖先缺失（`target_ancestor_missing`）、目标父目录不是目录（`subtree_changed`）。它们都不写意图、不动磁盘，wire 码取 `SUBTREE_CHANGED`（与 design §10.1“不覆盖目标、重新规划另名/恢复目录”一致）；源现场与基线不符取 `RECONCILE_REQUIRED`。
- **新建条目的身份必须不存在**：`entry_baseline` 返回成功即 `entry_already_exists`（`BASE_MISMATCH`），不复用别人的身份；新建的 revision 由事务分配为 0，核心在 `check_record` 里核对。
- **端口按现有风格分三处**：`ports::namespace`（目录动作）、`ports::namespace_store`（元数据事务，复用 `RootFacts`/`EntryBaseline`/`EntryKind`）、`ports::intent_log::NamespaceIntentLog`（与 `IntentLog` 共用 `fs_intents` 与 `PutPhase`，`kind = create/move`、`staging_path` NULL）。既有 `IntentLog`/`PutCommitStore` 未改动，put 路径零回归。
- **恢复是独立入口**：`recover_namespace_root` + `classify_namespace` 与 S037 的 `recover_root` 同一套不变量（Redo/Complete/Preserved/NeedsRecovery/Unresolved），但函数分开：S037 的 `recover_root` 只处理 put 意图，装配（S041）必须先跑两者再 `WriteAdmission::record`。没有把 namespace 硬塞进 `recover_root` 的签名，避免改动已验收的 API。
- **证据 JSON 复用同一编码器**：`intent.rs` 的 `parse_flat_object`/`take_*`/`finish_object` 提为 `pub(crate)`；路径按 UTF-8 十六进制（`path_hex`）编码，因为该编码器刻意不接受转义序列，而名称里合法可以出现 `"`/`\`。

## 3. 验证（devShell `nix develop --command bash -c '…'`，实际执行）

- `cargo test --locked -p vaultsyncd-server-core --lib` → 0，**101 passed / 0 failed**（S037 的 79 项全部仍通过，新增 22 项）。关键断言：
  - **目录移动只改父关系**：固定顺序 `root_facts → entry_baseline(条目) → entry_baseline(目标父) → inspect 源 → inspect 目标 → begin prepared → rename → inspect 源(空) → advance published → apply_namespace`；`record.entry` 仍是原身份、revision 从 3 到 4、`NamespaceWrite.from/to` 是 `(0x61,"docs")→(0x63,"docs")`、源路径空了、目标 inode 与源相同、轨迹里没有 `target publish`/`object`。
  - **文件移动保留内容引用**：`content_versions[条目]` 提交前后相同（假存储没有任何内容写路径）。
  - **新建目录**：顺序同移动但动作为 `mkdir`、`expected_revision`/`from` 为 `None`、事务后 revision 0；身份已存在 → `entry_already_exists`（`BASE_MISMATCH`）、不写意图。
  - **不覆盖目标**：目标已有文件/目录 → `target_occupied`（`SUBTREE_CHANGED`）；祖先缺失 → `target_ancestor_missing`；父目录是普通文件 → `subtree_changed`；三种情况都 `namespace_intents` 为空且没有 `mkdir`/`rename`。
  - **基线与环**：revision 已前进 → `base_mismatch`；条目已换父/名 → `subtree_changed`；目标落在自己子树、`to.parent == entry`、源与目标同路径 → `invalid_request`，均不动磁盘。
  - **源现场**：源不存在或种类变了 → `source_changed`（`RECONCILE_REQUIRED`）；`inspect` 报不可读 → `target_unreadable`，不当成“不存在”，不写意图。
  - **无假成功**：`rename` 满盘 → `no_space`、意图停在 `prepared`、无事务；`rename` 报告成功但 inode 不是源那一个、或源位置还在 → `applied_state_mismatch`、仍 `prepared`；事务报 revision 已变 → `base_mismatch`（阶段 `published`）；适配器返回阶段不是 `finalized` → `store_contract_violation`（`NEEDS_RECOVERY`）、`is_committed()` 恒 false。
  - **恢复矩阵**：`prepared` 且源在/目标空 → `Redone`（真的 rename 并补事务）；`prepared` 且源空/目标是同一 inode → `Complete`（**不再 rename**，只补事务）；目标已被占 → `Preserved{target_occupied}`（不 rename、不写事务，源保留）；`inspect` 不可读 → `NeedsRecovery{target_unreadable}`、意图落盘 `needs_recovery`、报告 `pauses_writes()`；新建的两种阶段同样按同一证据判定。
  - **证据 JSON**：往返一致（含带 `"`/`\` 的名称）；非规范写法（非 object、未知键、缺字段、类型错、非法十六进制、未知种类、after 为 `present:false`）逐项报对应 `StateJsonError` 码。

## 4. 限制

- **真实端口仍未落地**：`NamespacePort`（Linux 适配）、`NamespaceIntentLog`/`NamespaceCommitStore`（SQLx 适配）都只有假实现；`apply_namespace` 的“同一事务写 entries/changes 并收尾意图”要在 `crates/server-store` 落地后崩溃语义才在生产上成立。本卡证明的是**核心编排 + 端口契约**。
- **强杀矩阵只覆盖 put**：`tests/server-integration/` 的 SIGKILL 边界仍是 put 的九个边界；命名空间的崩溃恢复由假端口的阶段/现场组合覆盖（`prepared`+源在、`prepared`+源空、`published`+回退、不可读），未做真实进程强杀。
- **目标祖先只核对到父目录条目 + 端口现场**：`entries` 没有软删除父目录的可见标记，核心核对“目标父目录存在且是目录”，再依赖端口报告 `AncestorMissing`；逐级祖先遍历属平台适配器或后续卡的子树校验。
- **`deleted_at` 的父目录**：`EntryBaseline` 不含删除标记，若父目录被软删除，核心这一层看不到（同 S035 的边界）；恢复与 `SUBTREE_CHANGED` 的完整判断需要存储层补字段。
- **跨 Root 移动不在本卡**：design §9.5 的两段任务（目标创建成功后再删源）只有规划器侧（S022），执行侧属后续卡。
- **写入门未串起来**：`recover_namespace_root` 与 `recover_root` 是两个入口，装配顺序（先两者、再 `WriteAdmission::record`）只在文档里约束，S041 才能代码化。
