## 1. 接口决定

- **密码学只在一处**：`crates/server-core/src/auth/password.rs` 是本项目唯一引入 Argon2id 的地方（`argon2 0.5` + `password-hash` + `rand_core` 的 `getrandom` 只为 `OsRng`）。参数是常量 `m=19456 KiB, t=2, p=1`（RFC 9106 方向的工程基线）；**实测与 ADR 未做**，design §17.1 要求的“实测后写入 ADR”仍是欠账，但参数集中一处，且校验按散列自带参数，所以改默认值不需要重算旧散列（有测试锁定）。校验用白名单：只接受 `argon2id`，argon2i/md5/pbkdf2 一律 `Malformed`（数据坏了），不把“库认识这个算法”当许可。
- **初始化用例不写库**：`auth::init::prepare_owner` 只做“空状态 → 输入形态 → 散列 → 返回待写账号”，写由调用方在与 `count` **同一个写事务**里完成。这样两个 init 进程不可能都看到空表各写一行；端口 `OwnerAccounts` 的三个方法都是 `&mut self`，适配器可以持有那次事务。
- **没有默认密码，也没有默认密码的策略缺口**：登录名默认 `owner`（唯一账号的称呼），密码必须显式输入；密码规则 12 字符起（design 未给数值，取工程基线并集中成常量）、≤1024 字节、登录名 ≤64 字符且无控制字符。登录名不做大小写折叠（同 design §7.2 的“不偷偷规范化”）。
- **登录先限流再查账号**：`auth::login::authenticate` 的顺序固定为限流 → 查账号 → 比密码；不存在账号也做一次等代价计算（`dummy_verify`），账号不存在/密码错/账号未启用一律 `InvalidCredentials`（design §15.2“错误不暴露账号是否存在”）。唯一可区分的失败是 `AccountBroken`（已存散列损坏），只能由数据损坏触发，调用方必须记日志而不是透传成“凭据无效”。
- **限流是进程内、按登录名、按服务端时间**：默认 5 次/300 秒窗口/锁定 300 秒，不存在的登录名同样计数（否则“被限流”本身成为账号存在性信号），有 1024 条上限防内存放大。**按来源地址限流**需要 HTTP 层与代理头策略（design §17.2 不盲目信任 `X-Forwarded-*`），留给 S043/接入层。
- **会话不属本卡**：`POST /v1/auth/login` 的响应是会话，本卡没有 `sessions` 表也没有凭据发放，所以 **`api/openapi.yaml` 未改动**——生成器 `Operation` 是 `deny_unknown_fields` 且只读 `responses`，带请求体的端点在 S043 扩展生成器之前写不进契约（已记入 `docs/architecture/interfaces.md` 的生成器边界）。这是本卡唯一偏离“主要落点”的地方，理由是不写一个没有请求体 schema 的半截契约。
- **运行中 init 靠状态目录锁拒绝**：`crates/server-store/src/state_lock.rs` 独占 `<state_dir>/server.lock`（`fs2` 的 flock/LockFileEx，非阻塞，进程退出自动释放）。`apps/server` 在**打开数据库之前**抢锁（`StartupError::StateLock`），`vaultsyncd-admin init` 抢不到就退出码 3。没有用 pid 文件（崩溃后陈旧内容需要猜“pid 还活着吗”）。这条同时补上 S041 记的“单实例互斥仍靠部署约定”。
- **为什么用 `fs2` 而不是标准库**：`std::fs::File::try_lock` 从 Rust 1.89 起才稳定，而 workspace `rust-version` 是 1.85.0。先试过把 MSRV 提到 1.89，结果 clippy 的 MSRV 感知 lint 连锁要求改 `crates/domain`、`crates/fs-common`、`crates/server-core` 里与认证无关的代码（`as_chunks`/`is_multiple_of`/`let`-chain 折叠），为一张认证卡拖进 5+ 处无关改动，因此回退：**MSRV 保持 1.85.0，锁用 `fs2 0.4`**，代码里用 trait 全路径 `fs2::FileExt::try_lock_exclusive`（否则方法解析会选到 1.89 的标准库版本并被 `incompatible_msrv` 拒绝）。
- **init 不读密码的命令行参数**：`--password` 是未知参数（退出码 2）。密码只从 stdin 读：stdin 是终端时提示两遍且用 `rpassword` 关掉回显，是管道时读一行（去掉一个结尾换行）。输出只打印登录名、账号身份、数据库路径与“Argon2id”这一事实，**不打印密码也不打印散列**。
- **账户状态闭集目前只有 `active`**：迁移 0002 把取值集合留给本卡；新增状态时必须同时决定登录路径怎么处理它，因此不在此处预留用不上的变体。

## 4. 限制

- **登录还不是 HTTP 端点**：`auth::login` 只有核心用例与端口，接线在 S043（会话）。`api/openapi.yaml` 因此未动；带请求体的端点需要先扩展生成器（`Operation` 目前拒绝 `requestBody`）。
- **限流是进程内的**：重启清零，不按来源地址（HTTP 层才有），1024 条上限下极端情况会淘汰最久未出现的条目使计数归零。持久封禁与接入层限流未做。
- **Argon2id 参数没有实测与 ADR**：`m=19456,t=2,p=1` 是工程基线，design §17.1 要求的“结合目标服务器实测后写入 ADR”仍欠账；单次散列在开发机约几十毫秒，未做并发压测。
- **`users.status` 只有 `active`**：停用账号、密码重置失效（design §17.1 末段）属后续账号管理卡；新增取值时必须同时改登录路径。
- **状态目录锁只覆盖“同一状态目录”**：锁文件在状态目录里，不同目录自然互不影响；锁不防“同一个库通过符号链接/另一个路径访问”（`DATABASE_FILE_NAME` 固定，但状态目录本身可以是别的路径的别名）。
- **init 只有 `--state-dir`**：不读 `vaultsyncd.toml`，运维要保证该目录与服务端配置里的 `state_dir` 是同一个（未做“从配置读”的便利选项，避免两套来源）。
- **管理端仍只能离线改库**：运行中的管理动作（含重置密码）要等 S075 的本机管理 socket；本卡不提供绕过服务端的在线写路径。
