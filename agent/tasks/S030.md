## 1. 接口决定

- **新增独立 crate `crates/client-store`（包 `vaultsyncd-client-store`）**，进入 `members` 与 `default-members`（只有 SQLx + domain，无平台 API，便携检查可跑）。它与 `crates/server-store` **没有依赖关系**：两套 schema、两个数据库文件（design §5.4、§7.3）。
- **客户端库种类标识** `CLIENT_APPLICATION_ID = 0x434C4E54`（ASCII `CLNT`），写入 `PRAGMA application_id`。服务端用 `VSN1`（S026）。S026 的测试当时用 `0x434C4E54` 作为“任意异值”模拟客户端库，现在这个值成了真正的客户端标识，方向仍成立；本卡测试反向覆盖“客户端拒绝服务端库”，断言拒绝后 `application_id`、`user_version`、对方表结构与 `journal_mode` 原样保留，且没有建出任何客户端表。
- **打开/迁移/备份/事务逻辑按 S026 同一套规则重写在本 crate 内**（`src/db.rs`）：只读探测 → 种类门禁（空库可收养、未标记非空库与其它标识一律拒绝）→ 版本门禁（`user_version` 与 `_sqlx_migrations` 取大）→ WAL 读回校验 → 非空库且确有待执行迁移时 `VACUUM INTO` + `quick_check` 备份 → 迁移 → 写标记 → 建池（上限 4）；`begin_write()` 是 `BEGIN IMMEDIATE`，等锁 10 s。未抽共享 crate：design §5.4 没有共享存储层，新建它会改架构；重复部分记在限制里，留待后续整合卡决定。
- **`db.rs` 的 `open_with` 仍是私有**，测试用合成迁移集（0001 + `0002_probe`）验证升级备份与“schema 比二进制新”拒绝，不提前发布假迁移。
- **五张表**（`migrations/0001_initial.sql`）：`bindings`、`baseline_entries`、`remote_entries`、`local_entries`、`pending_ops`。`received_changes`/`transfers`/`local_intents`/`notifications` 留给 S031。
- **三张条目表之间没有外键**，各自只 `REFERENCES bindings(id) ON DELETE CASCADE`。这是本卡的核心决定：同一条目必须能同时保存“旧基线 + 新远端 + 本地 dirty”（design §7.3、§8.1、§8.4），任何一张表的写入/删除都不得约束另外两张；`remote_entries` 与 `local_entries` 也不引用 `baseline_entries`（首次同步 I07 与本地新文件在提交前都没有共同基线）。
- **位置用身份表达**：`parent_entry_id` + `name`；根条目 `parent_entry_id IS NULL` 时名称必空且只能是目录（Rust 层先给 `RootEntryShape`，SQL `CHECK` 兜底）。目录 `content_version_id` 必须为 NULL（design §7.1、I12）。
- **`bindings` 字段**：`id`、`server_id`、`device_id`、`root_id`、`local_path`、`cache_path`、`mode`、`rules_version`、`server_epoch`。`mode` 只有 `full`/`on_demand`（design C34），不接受未知值。路径只做“非空、无 NUL”形式检查：客户端可能是 Windows `C:\…`、Linux `/mnt/…`，绝对性与重叠判定需要平台语义，留给绑定流程（S058 起），本层不规范化用户路径。
- **`local_entries`**：`generation`、`dirty`、`residency`、`fingerprint`、`file_identity`。`dirty`/`residency` 文本与 design §8.1 拼写完全一致并由 `CHECK` 限定；空 `BLOB` 被拒绝（“未知”用 NULL 表示）。本层不生成 generation、不改写它，也不根据 `clean` 做任何破坏性判断（design §8.4）。
- **`pending_ops`**：`op_id` 主键、`binding_id`、`kind`（非空；取值集合留给执行器卡 S055）、`entry_id`（可为 NULL）、`baseline_revision`/`baseline_version_id`、`depends_on`（自引用、`ON DELETE RESTRICT`、禁止自依赖）、`pinned_version_id`、`attempts`、`last_error_code`（design §15.4 错误码文本，未知文本按坏行拒绝，不默认归为可重试）。队列顺序 = `rowid` 插入顺序，不使用客户端时钟（I04）。`record_attempt_failure` 只累加次数与最近错误；`complete` 删除行，仍有依赖方时因 RESTRICT 失败，不级联丢弃前置操作。
- **名称存原文**：客户端可能收到另一平台接受的名称，本层不归一化、不改写；跨平台可表示性由 fs-common 规则与同步流程判定。
- 读写接口风格与服务端存储一致：写函数接 `&mut Transaction<'_, Sqlite>`（调用方已开 `BEGIN IMMEDIATE`），只读函数接 `&mut SqliteConnection`（可直接用池，不为一次读取抢写锁）；身份列先读成字节再按 16 字节校验，坏行报 `MalformedRow{column}`。

## 4. 限制

- **`db.rs` 与 `crates/server-store/src/db.rs` 是两份同构实现**（~400 行门禁/迁移/备份/事务）。这是本卡的取舍：design §5.4 没有共享存储 crate，新增它属于架构变更；两 crate 也不该互相依赖。若后续卡要合并，建议抽 `crates/sqlite-store` 之类的共享层并同时改 design 与两套测试，需要单独决策。
- 每个绑定允许任意多条条目行，未加“同父名称唯一”约束：客户端要能保存服务器给的、与本地大小写/等价规则冲突的名字，冲突处理属规划与执行器（S019/S055）。
- 路径列是 SQLite `TEXT`：不能表示非法 UTF-8 的 Windows 路径（极少见）。绑定卡（S058 起）若要支持这类路径，需要在 `bindings` 上换成平台字节或加列并配迁移。
- 客户端库不在 SMB/NFS 上的“拒绝 WAL”只有代码路径，没有该环境的运行证据；指纹、file identity 的具体编码与“内容是否真的变了”的复核（design §8.4）属平台层与恢复卡（S037）。
- 队列顺序依赖 `rowid`（SQLite 隐式插入序）；若将来需要“可重排优先级”，要显式加列，不能继续依赖 `rowid`。
- 未建 `received_changes`/`transfers`/`local_intents`/`notifications`（S031），也没有任何 UC/执行器接线；`pending_ops.kind` 的取值集合、重试退避与 `pinned_version` 的实际续租都还没有实现方。
- 迁移前备份留在数据库同目录且不自动清理（与 S026 相同）。
