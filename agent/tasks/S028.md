## 1. 接口决定

- **四张表一次建出**：`versions` 同时依赖 `entries`、`objects` 与 `changes`（复合外键），`operations` 依赖 `changes`，因此 0003 一个迁移建 `objects`/`changes`/`versions`/`operations`。外键承担三条硬约束：版本只能引用**已登记对象**、只能写在**已记录的批次**里；committed 操作的 `root_seq` 必须真实存在。这直接支撑“回滚不暴露事件”与 design §11.2 步骤 7。
- **RootSeq 由 `changes::append_change` 独占推进**：读 `roots.seq` → `UPDATE … WHERE seq = 旧值` 比较并写 → 插批次行，全在调用方 `BEGIN IMMEDIATE` 事务里。受影响行数不是 1 报 `SeqConflict`，不盲目自增；`(root_id, seq)` 主键兜底。一个批次一行，分页只切行，因此目录级事务不会被拆半。
- **`changes_after` 越权报错而不是空列表**：空列表会让客户端以为“已追平”，把权限失败当成没有事件（与 I08 同类的错误在游标上的版本）。
- **版本与条目指向集中在一处**：`versions::record_version` 依次核对对象（存在且长度一致）、批次（存在）、条目（活跃文件），先给旧当前版本写 `superseded_at`，再插新版本，最后改 `entries.content_version_id`。部分唯一索引保证每条目至多一个当前版本；触发器保证历史行除 `superseded_at` 外不可改写（I12）。
- **`entries.content_version_id` 不加重建表外键**：SQLite 追加外键只能重建表，而 `entries ↔ versions` 互为引用（循环外键），重建需要在 SQLx 的迁移事务里 `PRAGMA defer_foreign_keys`，风险与收益不成比例。改为用唯一的写入路径（`versions::record_version` → `entries::set_current_content_version`，`pub(crate)`）+ 新建条目时的存在性核对（新错误 `EntryError::UnknownContentVersion`）达到同样的可见保证：不存在能写出悬空指针的公开路径。残留见 §4。
- **幂等键 `(root_id, device_id, op_id)` + 规范化语义摘要**：`request_digest` 只接受语义字段（名、值），拒绝空/重复字段名，按名排序后长度前缀编码再加固定语义版本前缀做 SHA-256（`sha2 0.10`，与内容哈希同算法，Cargo.lock 已有该版本）。字段顺序无关、语义不同必不同；调用方传语义值，不传原始请求字节或 JSON 文本。
- **状态机 `pending → committed | rejected` 都是终态**：`pending` 不带结果、不占 `root_seq`（迁移里 CHECK）；`commit_operation` 在同一个事务里追加批次并把结果与 `root_seq` 写入，重试路径是 `begin_operation` 拿到 `Replayed(记录)`，而不是重做；已终态再 `commit`/`reject`/`attach_intent` 报 `AlreadyFinished`。
- **紧凑结果保留规则**：只有终态存 `result_json`，必须是 JSON object 且 ≤ 4096 字节（Rust 侧用 SQLite JSON 函数给出 `InvalidResult`，迁移 CHECK 兜底）；记录保留到设备代际失效，届时由 `discard_finished_operations` 删除**终态**记录，`pending` 一律保留（删掉会让同一 `op_id` 被当成新命令重新执行，design §9.4）。
- **新增 `domain::ids::TxId`**：design §7.2/§9.3 的 `TxId` 此前没有类型，而身份只能在 `crates/domain` 定义（§7.1），因此按既有 `opaque_id!` 形状追加，并把身份清单测试扩到 9 种。
- **`objects.storage_path` 全库唯一**：两行指向同一物理文件时，按 Root 的 GC 会删掉别人的字节；跨 Root 共享字节若要做，需要独立的共享对象表，属设计变更。
- **`gc_state` 只有 `live`/`collectable`**：本卡只需要“不再接受新引用”这一个语义，更细的 GC 阶段属对象回收卡。

## 4. 限制

- `entries.content_version_id` 仍无指向 `versions(id)` 的外键（见 §1 决定）。残留缺口只有“绕过本 crate 直接写 SQL”这一条，公开写入路径已被唯一化 + 存在性核对堵住；补外键需要 `entries` 重建表（循环外键 + `defer_foreign_keys`），属单独的重建卡。
- `object_hash` 的正确性依赖平台层：本层只要求 32 字节并与对象登记长度一致，不重算 SHA-256（对象落盘与校验在 `crates/platform-linux-server`）。
- 事件的**内容**由调用方给出：本层只校验“非空 JSON 数组”，不定义事件 schema（事件 DTO 属协议卡）；`events_json` 的 JSON 形状依赖 SQLite 自带 JSON 函数（bundled SQLite 已内置，CLI 3.53.3 实测一致）。
- `TxId` 目前不唯一：一次提交可能给多个 Root 各写一批，设计未要求跨 Root 唯一，故只作关联字段。
- `object.gc_state` 只有两态、`discard_finished_operations` 的调用时机（设备代际失效）由后续设备/会话卡决定；本卡只提供被调用的入口。
- 上传（uploads/upload_parts）、冲突、回收站、fs_intents、backup_leases 五张表不在本卡范围。
