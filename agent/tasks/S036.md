## 1. 接口决定

- **新模块 `crates/server-core/src/commit/conflict.rs` + 新端口 `ports/conflict_store.rs`**，不新建 crate、不加依赖（server-core 仍只依赖 `vaultsyncd-domain`）。原因是冲突提交需要“源条目现状 + 幂等记录 + 原子冲突事务”三件 S035 没有的事实；把它们塞进 `PutCommitStore` 会让 put 的端口混进幂等状态机，故按 S035 的“一卡一端口”方式并列新增，二者由同一适配器实现。
- **核心只比较摘要，不重算**：`RequestDigest`（32 字节）由调用方用 `vaultsyncd_server_store::operations::request_digest` 对语义字段算出；规范化编码仍只有 `server-store` 一处（模块文档要求摘要覆盖源条目、基线 revision、冲突路径、内容摘要与长度，否则两个不同请求会被当成重试）。摘要相同但记录的源条目/路径/内容不同 → `store_contract_violation`（`NEEDS_RECOVERY`）停写核对。
- **顺序即不变量**：请求形状 → Root 票据 → `conflict_head`（epoch + 源条目现状）→ epoch → `operation` 记录 → “过期 + 不同内容”判定 → 目标空缺预检 → `begin_conflict`（登记 `pending`）→ `publish_put` → `apply_conflict` → 核对证据 → ACK。**幂等记录先于过期判断**：重放时 head 必然已前进，先判过期会把重试误判成 `conflict_not_stale`；**epoch 先于重放**（design §9.4 旧 epoch 不自动重放），重放时源条目已消失仍返回原结果（副本还在）。
- **只对“过期 + 不同内容”造副本**：head revision 仍是请求基线 → `conflict_not_stale`；head 内容已等于请求内容 → `content_already_committed`（§10.1 第二行，不额外造副本）。两者都映射 `RECONCILE_REQUIRED`，语义是“客户端事实过期，重新拉取再规划”。
- **冲突是普通受恢复保护的提交**：冲突条目走同一个 `publish_put`（意图 → 发布 → `published`）与元数据事务；发布失败停在 `prepared`、事务失败停在 `published`，意图行保留，`recovery::classify_put` 可直接分类。`apply_conflict` 在同一事务里做条目/版本/`conflicts` 映射/事件批次/`operations` 终态/`fs_intents` 收尾。
- **`pending` 不是 committed**：`begin_conflict` 原子“插入或读”，已存在时绝不改写摘要或结果；重试看到 `pending` 返回 `operation_pending` / `NEEDS_RECOVERY`，不重做也不造第二份副本。目标被占用这类**可重新规划**的拒绝放在登记之前（预检观察一次），避免把一个不可能完成的请求永久锁在 `OpId` 上。
- **名称不是身份**：`target_path` 仍由 `planner::conflict::conflict_entry_path` 生成（§10.2 只有一处实现），核心只校验 Root 内相对路径与单个名称分量；副本身份是核心用注入的 `IdSource` 分配的 `sibling`，与结果同事务持久化，重试不改名、不换 id。
- **wire 映射仍只有一处**：`PutFailureReason` 增 `OpIdReused`（`OP_ID_REUSED`）、`OperationPending`（`NEEDS_RECOVERY`）、`ConflictNotStale`/`ContentAlreadyCommitted`（`RECONCILE_REQUIRED`）、`ConflictStore`（透传存储码）；`put.rs` 的 `invalid_request`/`base_mismatch`/`reclassify_publish_failure`/`validate_name`/`validate_target_path` 改为 `pub(crate)` 复用，不另写一套规则。
- **未做**：真实 SQLx 适配与 `conflicts` 表（S028 只落了 `operations`）；崩溃后 `pending` 的收尾（S037）；HTTP 组装与三客户端端到端（S047 与执行器卡）。

- `cargo test --locked -p vaultsyncd-server-core` → 0，**66 passed / 0 failed**（S033—S035 的 48 项全部仍通过，新增 18 项）。按验收点的关键断言：
  - **过期不同内容只造一份副本**：跨端口顺序断言为 `store conflict_head → store operation → target observe → store begin_conflict → target observe → intent begin prepared → target publish → intent advance published → store apply_conflict`；副本 `sibling` = 服务器分配值、`source` = head 条目、`path`/`content` 与请求一致，工作目录发布摘要/长度等于迟到内容，Root 票据已释放。
  - **丢失响应后重试不多造副本**：第二次调用返回逐字段相同的 `CommittedConflict`，trace 片段只有 `conflict_head` + `operation`，`store.writes`/`target.publishes`/`log.intents` 计数都不增；源条目被删掉后仍返回原结果。
  - **同一 OpId 不同请求**：摘要不同 → `op_id_reused` / `OP_ID_REUSED`，不发布、不写映射；摘要相同但记录着另一份路径 → `store_contract_violation` / `NEEDS_RECOVERY`。
  - **pending 不重做**：`begin_conflict` 返回同名 pending（或上次事务失败留下的 pending）→ `operation_pending` / `NEEDS_RECOVERY`，重试不再发布。
  - **多设备不同内容均可按 hash 找到**（T02）：三台设备各自的迟到内容得到三个不同 `sibling` 与三份不同摘要、同一 `source` 映射；三台各自重试都拿回自己的副本，副本数不增。
  - **拒绝分支**：epoch 变化 → `epoch_changed`（且不读幂等记录）；revision 仍是基线 → `conflict_not_stale`；head 内容相同 → `content_already_committed`；源条目消失且无记录 → `base_mismatch`；目录 → `unsupported_entry`；目标已被占用 → `reconcile_required` 且**不登记 pending**；满盘 → `no_space` 停在 `prepared` 且保留意图；事务失败停在 `published`，重试得到 `operation_pending`；暂存名逃逸/冲突路径逃逸 → `invalid_request`（任何端口调用前）；同 Root 并发 → `root_commit_busy` 且不误释放别人票据。

## 4. 限制

- **真实存储未落地**：`ConflictCommitStore` 只有测试假实现；`apply_conflict` 要接 `entries`/`versions`/`changes`/`operations`/`conflicts` 与 `fs_intents` 收尾，其中 **`conflicts` 表尚未建**（S028 只落了 `operations`）。真实实现里“同一 OpId 只有一个结果”要靠 `(root_id, device_id, op_id)` 唯一约束 + `begin_conflict` 的插入或读；核心侧只能比较摘要。
- **`pending` 的收尾依赖 S037**：发布后崩溃留下的 `pending` 行没有终态，本卡让它稳定返回 `operation_pending`（`NEEDS_RECOVERY`），由全 Root 恢复按 `published` 意图收尾或标记 `needs_recovery`；在此之前该 `OpId` 无法完成。
- **跨进程并发**：Root 票据只在单进程内串行；多进程共享一份数据库时，重复执行靠目标路径已占用与数据库唯一约束兜底（同 S035 限制）。
- **目标空缺依赖两次观察**：预检与 `publish_put` 各观察一次现场，两者之间被外部占用时 `pending` 会被登记下来（`operation_pending` 直到恢复），不承诺消除这个竞态窗口。
- **名称不由服务端生成**：`target_path` 仍来自 `planner`；若调用方给的名字不合 §10.2 规范，核心只拒绝非法形状（路径逃逸/空分量），不规范的名字由规划层负责。
- **`conflicts` 的“原因”列未定形状**：本卡只在端口契约里要求写映射（源条目 → 冲突条目 + 原因），具体原因枚举与 `events_json` 属协议/存储卡。
