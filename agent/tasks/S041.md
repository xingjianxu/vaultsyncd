## 1. 接口决定

- **新包 `apps/server`（`vaultsyncd-server`）只做装配**：入口薄（参数、信号、退出码），配置校验在 `config`、依赖组装与启动顺序在 `bootstrap`、恢复结论在 `recovery`、准入与 readiness 在 `lifecycle`、HTTP 在 `http`。业务规则一律调 `server-core`/`server-store`，不在这里重写（design §5.3）。
- **Linux-only 是编译期约束**：非 Linux 目标直接 `compile_error!`，包进 `members` 不进 `default-members`；`cargo tree -p vaultsyncd-server` 无 fuse/cfapi/windows 依赖。服务端不需要 `/dev/fuse`（design §4.2、§17.2）。
- **配置严格、默认最少**：TOML 用 `deny_unknown_fields`——拼错的键必须报错，否则会带着默认值静默启动。默认监听 `127.0.0.1:8721`（回环 + 独立端口），状态目录必填、必须已存在且是绝对路径，数据库固定 `dir/server.sqlite`。服务不替运维决定内部目录落在哪个文件系统（btrfs 准入属后续存储卡，见限制）。配置错误退出码 2，且**不创建数据库**。
- **readiness 与写入门分两层**：`Lifecycle` 的 `Phase`（starting/ready/needs_recovery/draining）只表达“能不能对外声明可用”；逐 Root 的写入许可仍由 S037 的 `WriteAdmission` 决定，`Lifecycle::record_recovery` 是唯一开放入口，没有任何“直接打开”的旁路。停止时额外一条 `SubmissionRefusal::ShuttingDown`（码 `shutting_down`）。
- **未完成意图如实报告、不假装恢复**：`recovery::assess_registered_roots` 用新增的 `server_store::roots::all_roots`（系统级查询，不依赖 owner scope）取全部已注册 Root，逐 Root 读 `fs_intents` 未收尾行。空清单 → 记一份空 `RecoveryReport`（开放写入）；非空 → 计入 `blocked_roots`，`mark_needs_recovery(...)`，`/v1/health` 返回 503 `NEEDS_RECOVERY` 且 `retryable=false`。**没有**把“重启过”当恢复证据，也不清理证据行。真正重放需要 `PutCommitStore` 的真实存储适配（S035/S037 的已知缺口），本卡不伪造。
- **清单读不出来就不启动**：`assess_registered_roots` 的失败是 `StartupError::Recovery`，进程退出码 1——`IntentLog` 的契约是“读不出不能假设没有未完成意图”，不能降级成空清单。
- **优雅停止的顺序固定**：先 `begin_shutdown()`（新提交立刻被拒），再让 `axum::serve(...).with_graceful_shutdown` 收尾，然后统计并打印 `unfinished_intents=N`（证据账目），最后关数据库。停止流程不删除意图行、暂存或已发布内容。信号注册在组装依赖之前：拿不到 SIGTERM/SIGINT 处理就不接请求。
- **健康探测用生成的 wire DTO**（`vaultsyncd_protocol::generated`），不手写 JSON：`Ready`→200 `{"status":"ok"}`；`Draining`→200 `{"status":"degraded"}`（读可用、写已拒）；`Starting`→503 `NEEDS_RECOVERY`+`retryable=true`；`NeedsRecovery`→503 `NEEDS_RECOVERY`+`retryable=false`。`request_id` 为 `srv-<pid>-<序号>`（本卡还没有请求头解析）。
- **日志不写 ANSI**：非终端输出关掉颜色，否则 systemd/容器/验收断言拿到的是带转义符的文本。
- **未做**：`GET /v1/capabilities`（需要 ServerId/epoch 的真实来源）、认证与业务端点（S042—S044）；内部目录与 Root 的 btrfs 准入；跨进程单实例互斥。

## 4. 限制

- **未完成意图不会真的被恢复**：`recovery::assess_registered_roots` 只报“没完成”，不重放。真实重放要按意图证据核对现场、必要时补元数据事务，需要 `PutCommitStore`/`IntentLog` 的真实存储适配（S035/S037 缺口）。因此含未完成意图的状态目录会一直以 503 运行，直到该适配落地；这是刻意的 fail-closed，不是遗漏。
- **内部存储准入未接**：design §11.4 要求内部目录（SQLite/对象/历史/暂存/备份）在合规 btrfs 上，`crates/platform-linux-server::mounts` 已有判定；本卡只在配置层要求状态目录存在，未接准入检查（需要在哪个卡落地、如何在 CI 的非 btrfs 临时目录上测，留给存储组装卡决定）。
- **只实现 `GET /v1/health`**：`/v1/capabilities` 需要 ServerId/epoch 的真实来源（S042/S044），认证、Root、上传等端点在其后加入同一个 router；`request_id` 目前是进程内序号，还没有读取客户端请求头。
- **单实例互斥仍靠部署约定**：两个进程同时指向同一状态目录不会互相阻止（`WriteAdmission` 只在本进程内，同 S037 限制）。
- **状态目录必须事先存在**：服务端不自动创建目录，运维要在准备好后端与权限后手工建好；systemd 部署示例（`packaging/linux/systemd/`）尚未创建，属部署卡。
- **`Draining` 期间健康探测返回 200 `degraded`**：表示“还能读、新提交已被拒绝”；本卡还没有读端点，等业务端点加入后需要复核这个映射。
