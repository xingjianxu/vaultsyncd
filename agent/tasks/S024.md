## 1. 接口决定

- **单一编辑源 + 自研生成器**：`api/openapi.yaml`（OpenAPI 3.1.0）是远端协议唯一编辑源，`cargo xtask generate` 同时产出 Rust DTO（`crates/protocol/src/generated/mod.rs`）与 TypeScript 类型+客户端（`packages/api-client/src/generated/{types,client}.ts`）。**没有引入外部生成器**（openapi-generator/openapi-typescript）：前者会把 JVM 与 reqwest 拖进契约路径，后者的模板输出不受控且不产生运行时校验；改为在 xtask 内实现只支持本契约子集的生成器，新依赖只有解析器 `serde`/`serde_yaml_ng` 0.10/`toml` 0.9，版本由根 `Cargo.lock` 锁定，生成器版本身份写进 `api/generation.toml` 并在运行前核对（`format_version`/`generator`/`generator_version`/`openapi_version` 任一不符即失败）。
- **生成器失败优于猜测**：未实现构造一律报错（内联 `enum`、内联对象、`default` 状态码、非 components 的 `$ref`、映射值非 string、未知 `format`、文档/schema 未知键）；契约卫生也由生成器强制——具名 schema 与每个属性必须有 `description`（否则生成代码违反 `missing_docs`）、schema 名 PascalCase、字段 snake_case 且非 Rust 关键字、`required` 只能引用已定义属性、`operationId` 为 lowerCamelCase、恰好一个 2xx 响应、非 2xx 必须引用 `ErrorEnvelope`。
- **最小契约**：`GET /v1/health`（`HealthResponse`：`status` 闭集 `ok|degraded|needs_recovery`）与 `GET /v1/capabilities`（`Capabilities`：`protocol{major,minor}`、`server_id`、`epoch`、`features[]`、`limits{max_page_size,max_upload_part_bytes}`）；两者均无需认证（design §15.1），503 用错误信封。错误信封 `ErrorEnvelope{error:ErrorBody}`，`ErrorCode` 取 design §15.4 的 18 个远端码，本机 IPC 码（`LOCAL_CHANGED` 等）明确排除。
- **未知枚举不默认成功**：Rust 生成的枚举无 catch-all，TypeScript 侧 `decode<Enum>` 对未知取值抛错；`features` 是显式协商的可扩展标记集合，按“认识才用”保留，不套用闭集规则（这一点已写进契约 description，避免把两种语义混为一谈）。
- **长整数字符串**：`format: decimal_u64` 映射到 Rust `String` + `#[serde(with = "crate::decimal")]`（拒绝 JSON number、`"01"`、`"-1"`、超 `i64::MAX`）与 TS `expect_decimal()`（正则 `^(0|[1-9][0-9]*)$`）；`crate::decimal` 的规则与 `vaultsyncd_domain::version` 的规范十进制用同一取值矩阵测试比对。
- **domain → wire 显式转换**：`crates/protocol/src/domain_map.rs` 提供 `server_epoch_to_wire/from_wire`、`server_id_to_wire/from_wire`，不实现 `From`/`Into`；生成的 DTO 不认识 domain 类型，转换点集中在一处，后续带 domain 语义的字段按同一形状追加。
- **接线**：`crates/protocol` 进 `members` 与 `default-members`（纯核心、两端共用，便携 clippy/test 覆盖）；`packages/api-client` 进 `pnpm-workspace.yaml`，`src/index.ts` 是手写稳定导出面；`cargo xtask check` 新增第一步 `protocol-regenerate`（进程内 `generate --check`），CI 单步即含“重新生成无 diff”。

## 4. 限制

- 契约覆盖仅两个端点与错误信封；其余 §15.2 端点在功能卡中逐个加入，生成器子集会随之扩展（届时需同步更新 `api/generation.toml` 的 `format_version` 与本文档的子集表）。
- `CapabilityLimits` 的两个字段（`max_page_size`、`max_upload_part_bytes`）与 `features` 的取值集合是**临时最小集合**，尚无服务端实现背书；服务端落地（S041/S044）时可能调整。
- 生成器不支持 `oneOf`/`anyOf`/`nullable`/可空对象、嵌套内联对象与映射的非 string 值；需要时先扩生成器而不是手改生成代码。
- TS 侧只校验 wire 形态（枚举、必填、十进制文本、基本类型），不做完整 JSON Schema 校验；正式 Web 客户端接入时按需扩展。
- 生成器自身的“契约→代码”测试只覆盖 4 个正/负路径与端到端负控，没有做 OpenAPI 规范级一致性校验（无外部校验器依赖）。
- `packages/api-client` 运行时断言（`test`）不在 `cargo xtask check` 内（`check` 只跑 typecheck），协议相关卡需手动执行；CI 是否加这一步留给 S101。
