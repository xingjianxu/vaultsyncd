# S186 — 开发构建先清空 dist 且失败不留残骸

状态：done（验收与交接完成）。用户 2026-11-11 要求「build.sh 构建产物前，先清空 dist 目录」。原脚本虽在 `.#windows` 内先 `rm -rf dist/`，但清空发生在进入 devShell 之后，且暂存目录是 `dist/.stage`——S185 之后主工作区 `dist/` 里就残留着失败构建留下的 `.stage`。用户选定方案：清空提前到进入 devShell 之前，暂存目录移出 `dist/`，失败时 `dist/` 保持为空。

## 结果

`tools/build.sh`（唯一改动脚本，其余为文档）：

- 位置调整：`out=$vault/dist`、`stage=$stage_root/dev-build-stage` 提到参数校验之前计算；`stage_root=${CARGO_TARGET_DIR:-$vault/target}`，相对路径按仓库根解析（与原来 `built` 的解析方式一致）。参数错误仍退出 2，报错指向绝对 `dist/` 路径。
- 清空时机：在 `exec nix develop .#windows` **之前**就 `rm -rf "$out" "$stage"`；重入 devShell 时用 `VAULTSYNCD_BUILD_CLEARED=1`（经 `exec nix develop .#windows --command env ...` 传下去）跳过第二次清空，只打印一行「清空」。因此 devShell 起不来、前端失败或编译失败时，`dist/` 都不会保留上一轮旧产物。
- 暂存与搬运：全部中间物（`payload/` 四个 EXE、`installed-files.json`、`UNSIGNED-TEST.txt`、`unsigned.zip`、`payload/zip/` 成品、`build-info.txt`）都在 `target/dev-build-stage` 内组装；`zip_files` 齐套检查改在暂存区做；只有全部就位才 `mkdir -p "$out"` 并 `mv` 成品与 `build-info.txt` 进 `dist/`。`trap 'rm -rf "$stage"' EXIT` 覆盖成功与失败两条路径，`unsigned.zip` 照旧不进入 `dist/`。
- 不变项：前端重建、静态 CRT 交叉编译命令、`RUSTFLAGS`、`packaging/windows/zip/build.py` 复用的清单与整包复核、`build-info.txt` 字段、退出码语义、发布链（`tools/release.sh`、`packaging/release.py`、`cargo xtask release`）全部未改。

接口与语义见 `docs/architecture/interfaces.md` S184 两处（清空/暂存新增一段）；操作说明同步 `packaging/README.md`、`docs/operations/windows-lab.md` §12.2。

## 限制

- 清空是破坏性的：`dist/` 里手工放置的东西（例如临时解压的同源 ZIP）在下次构建时会一起消失，这是本卡要求的行为。
- 暂存目录与 `CARGO_TARGET_DIR` 共用；若两个构建并发指向同一 `CARGO_TARGET_DIR`，会互相删除暂存区。当前工具链假定单构建串行。
- 主工作区旧的 `dist/.stage` 残留未被本卡清理（S185 当时失败的遗留，下次在主工作区运行 `./tools/build.sh` 会自行消失）。
- 产物仍是 `unsigned-test` 开发构建，无收据/签名，不能当发布候选。
