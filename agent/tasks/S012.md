## 1. 结果

- **`cfapi::guard`（新，纯逻辑、宿主可测）**：把“已观察 generation + 使用保护”写成可逐条锁定的判定。`Verdict{Clean,Dirty,Busy,Unknown}`、`ProbeOutcome{Opened,Failed(code),Skipped}`、`UsageProbe{exclusive_read,exclusive_write,shared_read}`、`ContentCheck{Matched,Mismatched,Unverified}`、`Observation{is_placeholder,pin_state,in_sync_state,on_disk_data_size,logical_size,modified_data_size}`、`evaluate(&Inputs)->Decision{verdict,reason}`。规则顺序即保守程度：非占位符 → 已脱水 → pinned → 探测冲突(32/33⇒Busy，其它码⇒Unknown) → 探测未执行 → 内容非全本地 → 内容不符(Dirty) → 内容无法核对 → 两次哈希不一致(Busy) → 才 Clean。`reason` 是稳定拼写，客体脚本按它断言；宿主 10 个单测覆盖每条分支。
- **`cfapi::release`（新，仅 Windows）**：`run_protect` 只判定；`run_release` 先判定、**只有 `Clean`** 才 `ProviderSession` 连接 → `CfSetInSyncState(IN_SYNC)` → `CfDehydratePlaceholder(0, 逻辑大小, NONE, NULL)` → 复核 `on_disk_data_size==0`。`ReleaseOutcome{Released,AlreadyDehydrated,Refused,DehydrateFailed}`；`Refused` 明确表示**没有**调用平台写操作（`dehydrate_hresult=-`），`DehydrateFailed` 保留原始 HRESULT。已脱水条目直接短路（不探测、不读内容，避免“为判定而水合”）。探测是三次 `CreateFileW`（`GENERIC_READ`+share 0 / `GENERIC_WRITE`+share 0 / `GENERIC_READ`+全共享），只开句柄即关。
- **`cfapi::prototype` 变更**：`PlaceholderInfo` 增 `pin_state`，`EntryObservation` 增 `pin_state()`/`modified_data_size()`；`inspect` 的 in-sync 断言改为“`in_sync_state!=0` 只允许出现在**已脱水**条目上”（`release` 的 `CfSetInSyncState` 会这样留状态），已水合却自称 in-sync 仍失败；`cleanup` 对“探针目录非空”记 `cleanup.remove status=kept_not_empty` 并**继续注销**（否则 rename-over 的无效名字会让同步根永远注册着）。`hresult_from_io` 提为 `pub(crate)`。
- **`cfapi::raw` 追加**：`CfDehydratePlaceholder`、`CfSetInSyncState`、`open_with_share`，以及 `CF_IN_SYNC_STATE_NOT_IN_SYNC`/`CF_SET_IN_SYNC_FLAG_NONE`/`FILE_SHARE_ALL`/`GENERIC_READ`/`GENERIC_WRITE`/`ERROR_ACCESS_DENIED`/`ERROR_DIR_NOT_EMPTY`；`provider::{entry_path,require_entry}` 提为 `pub(crate)` 复用。
- **`examples/cfapi-prototype`**：新增 `protect --name`（只判定）与 `release --name [--expect released|refused]`；`released` 接受 `released`/`already_dehydrated`，`refused` 接受 `refused`/`dehydrate_failed`，`dehydrate_failed` 永不报成功。
- **脚本**：`common.sh` 增 `CFAPI_RELEASE_GUEST_DIR`/`CFAPI_RELEASE_ROOT`/`CFAPI_RELEASE_RENAME_ROOT`；新增 `run-cfapi-release.sh` + `guest-cfapi-release.ps1`（纯 ASCII：客体代码页 437 且 PS 5.1 无 BOM 时按 ANSI 解析，中文注释曾把语法打断）。脚本每个场景都重置到“刚 create + 已水合”，保存后立即记哈希与判定。
- **文档**：`docs/operations/windows-lab.md` 新增 §18（命令、判定规则表、边界表、限制与阻塞）并把“当前状态”改为 §19 追加 S012 条目；`docs/environment.md` 新增 §16；`docs/architecture/interfaces.md` 更新 platform-windows 的模块/命令/脚本/不变量。未改 `docs/design.md`、根 `Cargo.toml` lint 策略。

关键实测（build 26300.9457，`C:` NTFS）：

- **干净样本可释放**：`protect`=`clean`（`content=matched content_stable=true`，三探测 `opened`）→ `release`：`in_sync_hresult=0x00000000 dehydrate_hresult=0x00000000 on_disk_after=0`；新进程 `inspect` 退出 0（`dehydrated=true in_sync_state=1`）；再 `read` 触发 `FETCH_DATA`（`fetch_requests=1`）且哈希等于释放前。
- **原地写**（`FileShare.None` 覆盖前 100 B）：`modified_data_size=4096` → `dirty/content_mismatch` → `refused`、`dehydrate_hresult=-`、`on_disk_after=12345`、哈希不变。
- **映射写**（`CreateFromFile(path,Open)`+`WriteArray` 64 B）：`modified_data_size=12345` → `dirty` → `refused`、哈希与大小不变；**映射仍打开**时三探测 `error:32` → `busy` → `refused`，持有者退出后哈希变为映射写入值（`ea0d7e1a…`），文件仍在。
- **独占句柄 / 共享锁**：`FileShare.None` 三探测 `error:32`；`FileAccess.Read`+`FileShare.Read` 时 `probe_read_exclusive=error:32`、`probe_shared_read=opened`；两者都 `busy` → `refused`、哈希不变；独占持有者退出后同一内容 `clean` 且 `released`（证明拒绝来自使用保护）。
- **已脱水条目**：直接 `protect` → `unknown/already_dehydrated`，三探测 `skipped`（不为判定而水合）。
- **rename-over（阻塞）**：同步根内建临时文件失败（占位目录 `0x801F0005`、同步根顶层 `0x8007016A`，即使另一进程持有连接也一样）；改用同步根外同卷临时文件 `Move-Item -Force` 报告成功，但目标名字随后无法按路径打开（`0x801F0005`），`protect` 以 `stage=query.placeholder` 退出 1。恢复：`cleanup`（`kept_not_empty` 后仍注销）→ `inspect` 退出 3 → `rd /s /q` 成功（已实测）。

## 3. 阻塞与限制

- **rename-over 保存（T27/T28）无法证明安全**：现象见上。恢复条件：提供方要在被保存进程可见的范围内在线（打通 S011 记录的跨进程唤醒）并处理平台的重命名/删除通知，再重跑 `run-cfapi-release.sh` 里 `rename_over_*` 断言。脚本把该现象记成 `blocked_item=rename_over` + `check=pass name=rename_over_limitation_recorded`（断言的是“无法验证”这一事实，不是“保存成功”）。
- **干净判定需要读整份内容**，所以“已脱水→判定→释放”会先水合再脱水；真实实现要靠已记录的内容哈希/代际 + 短期内容租约（design §8.4）。
- 释放进程内紧跟 dehydrate 的 find-data 状态位滞后（`dehydrated_after=false` 而 `on_disk_after=0`）；复核一律用新进程 `inspect`。
- 共享模式探测看不到“完全共享”的读写者；`in_sync_state=0` 不等于 dirty（本原型从不自动置位）。只在 `C:` NTFS、build 26300 上实测；ReFS、非系统卷、Explorer 展示、真实编辑器（Word/VS Code）保存路径未验证。
