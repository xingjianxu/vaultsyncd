## 1. 接口决定

- **迁移 `0002_events_transfers_intents.sql`** 追加 `received_changes`、`transfers`、`local_intents`、`notifications` 四张表，并给 `bindings` 加 `received_seq`/`applied_seq` 两列（默认 0、`CHECK >= 0`），schema 目标版本 `1 → 2`。`0001` 未改写。
- **游标放在 `bindings` 行上**，不新建游标表：design §7.3 的表清单保持九张不变，游标与 `server_epoch` 同属一个绑定；`applied <= received` 由 `events::*` 的写入路径维护（SQLite 的 `ALTER TABLE ADD COLUMN` 不支持跨列 `CHECK`）。
- **`received_changes` 与服务器批次同形**：主键 `(binding_id, seq)`、`seq > 0`（0 只是“还没有批次”的游标值）、`tx_id` 16 字节 BLOB、`events_json` 为 JSON 数组文本（`json_valid` + `json_type='array'` 兜底）。`state` = `received`/`applied`/`blocked`，`last_error_code` 只在 `blocked` 出现。
- **`events::receive_batch` 一次事务写四件事**：批次行 → `remote_entries` → `pending_ops` → **最后**推进 `received_seq`（I09：不能先推进游标再写任务）。重复批次（同 seq、同 tx、同事件列表）返回已存记录且不重复入队；同 seq 不同内容 `ConflictingBatch`；seq 不大于游标 `StaleBatch`。
- **应用游标单独**：只有 `mark_batch_applied` 会推进 `applied_seq`，且只推到“连续已应用前缀”的末端；中间有未应用或阻塞批次时游标停在它之前（design §9.3“相关依赖不得越过”）。`mark_batch_blocked` 记原因但不删批次。
- **`transfers` 只记入站下载**：主键 `(binding_id, version_id)`，位图第 i 位 = 第 i 块（低位在前），长度由块几何 `CHECK` 约束、尾部 bit 必须为 0；`completed` 要求 `verified = 1` 且位图覆盖全部块；`running` 之外的状态拒绝进度更新，终态只能 `discard_transfer`。上传进度以服务端 `upload_parts` 为准（§9.3“不能只相信客户端位图”），不在客户端重复维护。
- **`local_intents` 用本地整数序号**：`intent_id INTEGER PRIMARY KEY`（插入序 = 恢复顺序，不是 wire 身份，与 `pending_ops` 的 `OpId` 不同），`UNIQUE (binding_id, target_path)` 保证同一路径同时只有一个期望；`kind` = `replace`/`move`/`release`/`import`；失败只转 `failed` 并保留路径、哈希、generation，完成才删行。
- **`notifications` 以 `dedupe_key` 为主键**：`binding_id` 可为 NULL（缓存盘满这类全局问题）；重复上报只加 `occurrences` 且**不重置已读**，`resolved` 后复发回到 `active` 且置未读（§18.2 不反复弹窗但也不藏复发）；同键换 `code` 报 `CodeMismatch`。
- **额外新增 `src/notifications.rs`**：卡片的“主要落点”只列三个文件，但四张表需要四个模块；沿用 S030“一表组一模块”（bindings/entries/queue）的既有结构，没有把通知塞进 events/intents。

## 4. 限制

- **`received_changes` 没有保留期/GC**：批次行只增不删。design §9.4 的事件保留期属拉取卡；在那之前长期运行的客户端需要一条按 `applied_seq` 清理的规则。
- **`receive_batch` 允许序号跳跃**：只拒绝不大于游标的批次，缺少的中间 seq 视为可用 `changes?after=` 补齐；应用游标因此可能停在缺口前，这是有意的保守行为。
- **游标只随绑定行存在**：`server_epoch` 改变或重新绑定会重建绑定行、游标回 0（旧游标失效，design §9.4）；没有“同一绑定内换 epoch 保留补拉位置”的机制。
- **`local_intents` 只持久化意图**：受控替换、哈希核对、generation 比较与文件身份校验都属平台/执行器卡；本卡不保证“写入意图后一定完成”。
- **`transfers` 不含出站上传与内容租约**：上传已收块以服务端为准；`pinned_version_id` 续租由 `pending_ops` 与后续卡处理。
- **通知不决定通知时机**：进入系统通知、5 秒/30 秒时限与合并文本属界面层（design §18.2）。
- **`notifications.rs` 超出卡片“主要落点”清单**：理由见 §1 最后一条；如评审要求严格按三文件落点，可合并进 `events.rs`，但那会把两个独立状态机塞进一个模块。
- 仍然保留 S030 的既有取舍：`db.rs` 与服务端 `db.rs` 是两份同构实现；`pending_ops.kind` 取值集合、重试退避与执行器接线仍留给 S055 起。
