## 1. 接口决定

- **删除复用 put/命名空间的阶段机**：`commit_delete` 走「请求形状 → Root 串行化 → epoch → 基线 revision → 子树忙 → 现场种类 → 冻结清单与 token → `prepared` 意图 → 有界批次移除并复核 → `published` → 单一事务 → ACK」。失败一律 `is_committed() == false`，已写意图保留为恢复证据。本卡只在 `fs_intents.kind` 里补 `delete`（迁移 0004 已允许），没有改 put/命名空间的行为。
- **子树 token 是服务端按冻结清单算的 128 位摘要**（FNV-1a，无第三方依赖）：清单里任一条目的身份/父目录/名称/种类/revision/内容版本变化或成员增删都会换值。客户端把上次拿到的 token 带回来，核心重算后比较；不等就 `subtree_changed`，不写意图、不动磁盘（T12）。文件删除必须不带 token、目录删除必须带，混用是 `invalid_request`——两种形态不靠“忽略多余字段”糊过去。
- **冻结清单是唯一事实来源**：`SubtreeImage`（目标自身 + 全部活跃后代，顺序由端口保证稳定）同时派生 token、有界批次（每批 ≤ `MAX_DELETE_BATCH_ENTRIES = 256`）与回收站清单，事务里不再二次读库。构造时校验根条目唯一且带父目录、身份不重复、路径合法、非根成员的父节点在清单里。
- **“大目录删除是有界批次任务”落在两处**：工作目录侧 `RemovalPort::remove_directory_batch(path, max_entries)` 循环到 `complete`（假端口把每批上限压到 2 来证明核心真的循环），数据库侧 `DeleteApply.batches` 按 256 切分。两者都是可中断、可重入的：数据库在最终事务前完全没动，重跑只需再删工作目录。
- **工作目录移除失败不能 ACK**：任一 `RemovalError`、或移除报告完成但复核现场仍存在（`removal_incomplete`），意图停在 `prepared`、不写元数据事务；`DeleteFailure::is_committed()` 恒为 `false`（design §10.3 第三条）。
- **子树忙 = 未收尾的删除意图**：忙标记不靠内存状态，而是持久事实。`SubtreeBusy::from_intents(&log.unfinished_deletes(root))` 之后 `check_write(root, path)` 对子树根与后代返回 `SubtreeBusyConflict`；`commit_delete` 自己在写意图前也用它拒绝重复/嵌套删除。wire 仍用 `SUBTREE_CHANGED`（design §15.4 没有 `SUBTREE_BUSY` 码，新造一个会越出已确认的错误契约），内部稳定码是 `subtree_busy`。
- **单一事务公布逻辑删除批次**：`DeleteStore::apply_delete` 拿到批次 + 回收站清单（`deleted_at`、`expires_at = deleted_at + 30 天`）+ 事件，在一个事务里写清单、墓碑、分批软删除、`changes` 与意图 `published → finalized`。任何一样失败都不能 ACK；返回证据与请求不一致按 `store_contract_violation` 停写（wire `NEEDS_RECOVERY`）。
- **删除不动内容与历史**：存储层不写 `objects`/`versions`、不改 `entries.content_version_id`；测试用真实 SQLite 证明删除后 `version_history` 仍返回旧版本、内容对象仍登记，随后在同路径建新条目 + 新版本，旧版本哈希不变。
- **恢复与命名空间同风格**：`classify_delete` 只看阶段与现场——路径不存在 → `Complete`；现场还是前提那个条目（同种类同 inode）→ `Redo`；被换成别的条目 → `Reconcile{target_occupied}`；祖先缺失 → `Reconcile{target_unavailable}`；读不到或已标 `needs_recovery` → `NeedsRecovery`。补事务前要求重读清单的 token 与条目数仍等于意图值，否则 `Unresolved("subtree_changed")` 停写——冻结后新冒出的子条目不会被悄悄一起删掉。

## 3. 验证（devShell `nix develop --command bash -c '…'`，实际执行）

- `cargo test --locked -p vaultsyncd-server-core --lib` → 0，**122 passed / 0 failed**（S038 的 101 项全部仍通过，新增 21 项）。关键断言：
  - **文件删除**：轨迹顺序是 `intent begin delete prepared` → `namespace remove_file notes.txt` → `intent advance published` → `store apply_delete`；回收站行保留 `path`/`parent`/`revision`/`content_version`，`expires_at = deleted_at + 30 天`；意图 before 的 token 等于冻结清单 token、条目数为 1。
  - **目录删除有界批次**：5 项清单、假适配器每批 2 项 → 至少 2 次移除调用、最终路径不存在、`removed = 5`，事务里的批次**完整覆盖**清单每一项；`SubtreeImage::batches(2)` 单测断言 3 批、每批 ≤ 2、合起来等于全树，`batches(0)` 报错。
  - **并发新增让前提失败（T12）**：旧 token ≠ 新清单 token → `subtree_changed`（wire `SUBTREE_CHANGED`），没有写意图、没有移除调用、没有事务，并发新增的文件仍在。
  - **形态与基线拒绝**：目录不带 token / 文件带 token → `invalid_request`；revision 过期 → `base_mismatch`。
  - **故障不是不存在**：`inspect` 不可读 → `target_unreadable`，不写意图、不动磁盘。
  - **移除失败不能 ACK**：`path_in_use` → 意图停在 `prepared`、无事务、文件仍在；“报告完成但路径还在” → `removal_incomplete`（wire `SUBTREE_CHANGED`）、仍 `prepared`、无事务。
  - **子树忙**：存在未收尾删除意图时，删除同一子树 → `subtree_busy`（不写第二条意图、不动磁盘）；`check_write` 对子树根与后代报忙，对兄弟路径与别的 Root 放行，意图收尾后不再挡路。
  - **无假成功**：事务返回 `trashed` 与清单不符 → `store_contract_violation`（wire `NEEDS_RECOVERY`）；事务失败 → 失败停在 `published`，`is_committed()` 为 false。
  - **恢复矩阵**：`prepared` + 现场仍是那一个条目 → `Redo`（真的重做移除并补事务）；路径已不存在 → `Complete`（不再删磁盘，直接补事务）；被换成普通文件 → `preserved{target_occupied}` 且不动别人的新内容；`inspect` 不可读 → 落 `needs_recovery` 且报告停写；冻结后又出现新子条目 → `Unresolved("subtree_changed")` 停写。

## 4. 限制

- **真实端口仍未落地**：`RemovalPort` 的 Linux 实现、`DeleteIntentLog`/`DeleteStore` 的 SQLx 适配、以及 `commit_delete` 的进程内装配都还没有；本卡证明的是核心编排 + 端口契约 + 表约束。真实删除的崩溃语义要等装配后才会在生产上成立。
- **`SubtreeBusy::check_write` 还没接进 put/新建/移动**：本卡只把它接进 `commit_delete`（拒绝重复/嵌套删除），其他写路径的调用点属于装配层的排期。
- **子树忙的 wire 表达**：design §15.4 没有独立 `SUBTREE_BUSY`，本卡用 `SUBTREE_CHANGED`（409，客户端拉最新事实后重新规划）。若产品要区分“忙”，需要走 design §24 的规格变更。
- **冻结后新增子条目的恢复走停写**：`Complete`/`Redo` 补事务前要求重读清单 token 相等。清单根已被别的删除带走时给 `Preserved{subtree_already_deleted}`（不暂停写入、需要协调），这类陈旧意图的收尾没有自动化，留待装配/协调卡处理。
- **墓碑与内容回收不在本卡**：只建表与写入路径，回收站过期后的内容回收、墓碑压缩与旧设备基线重建（design §10.3 末条）属同步协议卡；回收站恢复（含目标占用时另名恢复）属 S040。
- **强杀矩阵只覆盖 put**：`tests/server-integration/` 的 SIGKILL 边界仍是 put 的九个边界；删除的“中断可继续”由假端口的阶段/现场组合覆盖（`prepared` + 路径还在、`prepared` + 路径已消失、不可读、清单变化），未做真实进程强杀。
- **原生 `/proc` 之外的平台**：`RemovalPort` 契约要求“删除按批、失败不谎报”，但真实 Linux 实现（`unlinkat`/目录项遍历）尚未写，Windows 侧不涉及删除工作目录（服务端只在 Linux）。
