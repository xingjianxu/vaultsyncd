## 1. 接口决定

### `crates/transfer`（主要落点，仍不做 I/O）

- **执行器 + 端口**：新增 `ports.rs`，定义 `SnapshotSource`（固定快照读取）、`UploadTarget`
  （begin/status/put_part/finalize）、`VersionedContent`（固定版本区间读）、`TempContent`
  （临时文件写入/sync/discard/空间检查）、`DownloadProgressStore`（位图持久化）。端口失败统一分类为
  `PortError::{Unavailable{retry_after},ReauthRequired,Cancelled,Rejected{code},Protocol,Local{kind}}`，
  退避与调度仍属 `crates/agent-core`；本 crate 不读时钟、不发请求、不写文件。
- **`bitmap.rs`**：`PartBitmap`（第 i 位 = 第 i 块、低位在前、长度与尾部 bit 必检）与
  `PartRange`（缺失区间）。位图只有一种字节表示，`from_bytes` 对长度/尾部不符一律拒绝。
- **`upload::run` 顺序固定**：流式算整份摘要（窗口 ≤ 块大小）→ 续传先比对快照身份/大小/摘要，
  变了直接 `SnapshotChanged`（**不碰旧会话**）→ `status` 复核会话（总大小、整份摘要、块数必须等于
  快照）→ 只按服务端 `missing` 补块 → 回执的索引/长度/摘要都要一致，不符则重读快照重传
  （`part_attempts`，默认 2），持续不符 `PartRejected` 且不 finalize → `finalize` 再核对
  hash/size/part_count。返回 `ContentReference`（+`session`、`uploaded_parts`、`reused_parts`、
  `resumed`），**没有 committed 标志**：条目 head 由上层 `OpId` CAS 提交。
- **混版本防线**：摘要相同即内容相同（SHA-256），因此会话摘要 = 快照摘要时复用旧会话安全；不等时
  立即 `SessionMismatch`。另核对“服务端缺失区间”与“已收块”自洽（长度、重复索引、区间必须正好是
  已收块的补集），避免按错误缺块清单补块。快照身份（`SnapshotSource::identity`）变了也拒绝续传。
- **`download::run` 顺序固定**：固定 `VersionPin{binding,entry,version,digest,size}` → 载入位图
  （块几何/总大小/临时路径任一不符即作废）→ `ensure_capacity`（不足 `NoSpace`，不写、不删）→ 只取
  缺失块写入临时偏移 → `sync` → 流式读回临时文件算整份摘要 → 相符才返回 `DownloadOutcome`
  （摘要、大小、块数、临时路径、本次块数、是否续传、尝试次数）。不符则清位图与临时内容、有限次重下
  （`content_attempts`，默认 2），仍不符 `ContentMismatch`（**不安装**）。安装/发布意图/状态更新是
  上层的事，执行器从不覆盖用户文件、也不把下载完成当 committed。
- **有界块并发与取消**：`concurrency::bounded_join` 在单线程 executor 里以不超过 `part_concurrency`
  （默认 4，可调）推进块 future，遇错停止启动新块并丢弃在飞的 future；`CancelToken` 在“开始下一块
  之前”与摘要流式读取中检查，取消后已收到的块与进度全部保留。跨文件的并发仍由 agent 执行器控制。
- **明确不做**：跨版本块增量/内容定义分块/增量 GC（design §13.1）。位图只在同一次传输的有效性内
  使用，摘要或几何变了即作废。

### `crates/http-client`（端点包装）

- `uploads::UploadEndpoint<T>`（`UploadTarget` 实现）：`POST /v1/roots/{root}/uploads`、
  `GET …/uploads/{upload}`、`PUT …/uploads/{upload}/parts/{index}`（`x-part-sha256` 必发）、
  `POST …/uploads/{upload}/finalize`（无请求体）。Root 与会话身份先校验为 32 位小写十六进制。
- `content::ContentEndpoint<T>`（`VersionedContent` 实现）：`GET …/entries/{entry}/versions/{version}/content`
  + `Range: bytes=start-end`。核对 `Content-Range` 的起点/长度/总长、响应体长度与 `x-content-sha256`；
  整份 200 响应只接受“从 0 开始且长度等于版本大小”。
- `map_error`：`ClientError` → `PortError`（可重试/需重新登录/拒绝+错误码/协议/取消）；
  证书与协议错误一律不可重试。`parse_u64`/`parse_digest`/`is_identity`/`require_identity` 是规范
  十进制与标识形态的唯一入口，非法响应体一律协议错误，不猜、不截断。

## 4. 限制与阻塞

- **上传进度的本地持久化没有随本卡落库**：上传续传以服务端 `upload_parts` 为权威（design §9.3），本卡
  返回可持久化的 `UploadResume{snapshot,session}`，由上层（S055 agent 执行器）写进 operations/`pending_ops`。
  下载进度端口 `DownloadProgressStore` 已定形并可用内存替身验证跨重启语义，**SQLite 适配器尚未实现**；
  `crates/client-store` 的 `transfers` 表（S031）已有 `bitmap`/`temp_path`/`chunk_size`/`total_size` 列，
  适配器可直接映射，属 S055 的接线范围（本卡不改 client-store schema，避免与并行卡抢迁移编号）。
- **没有真实服务端联调**：端到端用例用 `FakeTransport` 实现契约端点（请求形状与 DTO 都是真的），没有对着
  `apps/server` 的监听跑；真实实例属 S097 部署卡与 S052 闭环。
- **整份摘要续传需要重算**：续传前必须重新流式哈希整份快照（不信任 mtime，design 禁止据此决胜），大文件
  续传有一次性读放大；后续可用“块摘要缓存”优化，但不能跳过内容校验。
- **下载错块只能整份重下**：服务端不提供每块摘要，整份摘要不符时无法定位坏块，按 design §13.2 做有限次
  重新下载（`content_attempts`）。
- **`x-part-sha256` 仍未进契约**（S045-b 的已知缺口）：客户端按 S045-b 实现发送，契约层仍只在描述里写。
- 未做每 Root/每会话的上传并发上限、同一文件的多 Op 合并、`Retry-After` 的 HTTP-date 形式（后者属调度）。
