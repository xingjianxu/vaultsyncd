## 1. 接口决定

- **五张表一次建出（0004）**：`uploads`/`upload_parts`/`fs_intents`/`backup_leases` 是 design §7.2 的四张表，`object_leases` 是 §19.4“上传/下载租约”和 §11“短期内容租约或等价机制”所要求的下载/提交对象保护模型。它们共同支撑同一条恢复边界——未完成意图、未齐全的块与有效租约都是持久化事实，重启后只靠数据库回答，不重放普通日志。
- **`uploads.chunk_size` 是设计要求的补充列**：§7.2 只列 `expected_size`/`hash`，但 §13.1/§15.2 的会话契约是“总大小 + 总 SHA-256 + 块参数（块含 index/length/hash）”，没有块大小就算不出块数与每块期望长度，“已收/缺哪些块”也无法给出确定答案。因此 `chunk_size` 随会话落库，由 `ChunkGeometry` 派生块数（`ceil(total/chunk)`，空内容 0 块）与每块期望长度。
- **块索引唯一 = 主键**：`(upload_id, part_index)`；相同索引只有长度、哈希、路径全同才是幂等重传（`AlreadyPresent`），否则 `PartConflict` 且旧行不被覆盖（§13.1“相同 index 重传若哈希不同返回错误”）。`upload_parts.path` 全库唯一，避免按会话清理删掉别人的字节。
- **上传状态四态、转换显式**：`open → complete | aborted`，`complete → finalized | aborted`，终态不再变化。`complete` 只表示“块齐且逐块核对通过”，不表示内容已成版本（总哈希校验与对象固定属 S046）；`mark_upload_complete` 用缺块查询兜住 I05，`mark_upload_finalized` 只接受 `complete`。放弃（客户端取消/会话过期）保留已收块行作为清理证据。
- **缺块用连续区间表示**：`UploadProgress.missing: Vec<MissingRange{first_index,count}>`，长度最多“已收块数 + 1”，不随文件大小增长（大文件逐块列举会放大成百万项）。
- **`session_id` 只校验长度，不建外键**：`sessions` 表属会话卡（S043）；SQLite 追加外键要重建表，本卡不提前造一张假会话表，也不假装校验会话有效性（§13.2 的“校验会话仍有效”由 API 层在本模块之前完成）。
- **`fs_intents` 带 kind、目标/暂存路径与两个 JSON 状态**：§7.2 列了 `expected_before`/`desired_after`/`phase`，§11.2 步骤 5 要求意图含“前后内容引用及恢复所需路径”，因此额外落 `kind`（`put_content`/`create`/`move`/`delete`，§11.2 末段说明移动/创建/删除同样用意图日志）、`target_path`（Root 内相对路径）、`staging_path`（可空）、`created_at`/`updated_at`（恢复需要稳定顺序与推进时间）。
- **“当时不存在”不用 NULL 表达**：两个状态列都是 `NOT NULL` 的 JSON object（迁移 CHECK 与本层预检查同一套 SQLite JSON 语义）。NULL 只能表示“未知”，把“不存在”混进未知里，恢复时无法区分“新建”和“读不出来”；具体字段编码属 S034（提交意图状态机），本层只保证形状。
- **phase 转换表**：`prepared → published | needs_recovery`；`published → finalized | needs_recovery`；`needs_recovery → finalized`（唯一人工出口，禁止退回 `prepared`/`published`，否则会把“无法解释”重新当成“可以重做”）；`finalized` 终态。时间戳必须单调，否则恢复顺序失去意义。`unfinished_intents` 列出 `phase <> 'finalized'`（含 `needs_recovery`），按 `created_at, intent_id` 升序。
- **`target_path` 受约束**：非空、无 NUL、不以 `/` 起始、无空分量与 `.`/`..` 分量。恢复会拿它定位工作文件，把 `../` 写进库等于把恢复指向 Root 之外；判定按服务端路径语义而不是宿主 `Path`（便携检查在 Windows 也跑这些测试）。
- **对象租约只保护已登记对象**：`object_leases(root_id, object_hash) → objects(root_id, hash)`（复合外键 + `ON DELETE RESTRICT`）。未落盘的哈希保护不了任何字节，写租约直接 `UnknownObject`；反向拒绝删除仍被租约保护的对象行，GC 与租约因此共用同一份引用协调（§19.4）。`expires_at > now` 是唯一有效期判据；释放幂等（第二次 `false`），写入相反——重复身份报 `DuplicateId`，不覆盖保护范围。
- **`backup_leases` 跨 Root、无 owner 列**：§7.2 只有 `id`/`snapshot_seq_map`/`expires_at`/`manifest_ref`。`SnapshotSeqMap` 按 Root 身份升序规范化，键是 32 位小写十六进制、值是 `RootSeq` 的规范十进制**文本**（§7.1：计数在文本里传，避免 2^53 精度问题），解析用 SQLite 的 `json_each` 并要求值类型是 text，因此“值写成 JSON number”的半规范数据按坏行报错，而不是悄悄接受两种写法。管理 API 的鉴权属 S087。
- **domain 追加 5 个身份**：`SessionId`、`UploadId`、`IntentId`、`ObjectLeaseId`、`BackupLeaseId`，身份只能定义在 `crates/domain`（§7.1），并扩展身份清单测试。

## 4. 限制

- **本层不校验字节**：块哈希与总哈希只存字节，长度只与块几何比较；真正的 SHA-256 计算、暂存文件落盘与 fsync 在 S045（接收）与 S033（对象）里完成。
- **`session_id` 无外键、不校验会话有效性**（见 §1 决定）：`sessions` 表属 S043，届时若要加外键需重建 `uploads`。
- **`uploads.state`/`fs_intents.phase`/`fs_intents.kind` 的取值集合写死在迁移 CHECK 里**：新增取值需要重建表，属 schema 变更；本卡按 design 的四态/四阶段/四种类建足，未预留未定义的取值。
- **意图不强制“同一路径同时只有一个未完成意图”**：并发序列化是 S034 的每 Root 提交调度锁职责；本卡只提供证据表与阶段转换。恢复链无法解释时进入 `needs_recovery`，不再自动推进。
- **未完成意图与终态意图都不自动清理**：`finalized` 行保留作为审计证据；按年龄清理需要一个明确的保留策略（属恢复/GC 卡），本卡不擅自定保留期。
- **`backup_leases` 读接口不带 owner scope**：设计里该表跨 Root 且没有归属列；把租约暴露给管理 API 时的鉴权属 S087。
- **`object_leases` 不做 GC 协调**：GC 标记（S085）与删除协调（S086）要用 `active_object_leases` 作为额外引用；检查后竞态删除由那条统一协调路径负责，本层只保证“租约存在则对象行删不掉”。
- conflicts、trash 两张表不在本卡范围。
