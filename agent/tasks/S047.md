## 1. 接口决定

- **两个端点**（契约先进 `api/openapi.yaml`，再用 `cargo xtask generate` 生成双端 DTO）：
  - `POST /v1/roots/{root}/operations` → `OperationRequest` → `200`（committed/rejected）、`202`（pending）、
    `400/401/403/409/410/422/503/507`。
  - `GET /v1/roots/{root}/operations/{op}` → `200`（终态）、`202`（pending）、`401/403/404/503`。
- **幂等键 `(root, device_id, op_id)`**：design §7.2 的键要求设备身份，而首发没有设备注册表，因此
  `device_id` 作为必填 wire 字段由客户端安装实例自报（不作为授权依据，只划定幂等范围）。
- **结果查询只带 OpId**：记录里的设备由库给出（新增 `server-store::operations::operation_of_root_in_scope`，
  同 Root 同 OpId 多行 → `DuplicateOperation`，不猜一个）。
- **摘要只覆盖语义**：`kind`/身份/基线/上传/本地代际/冲突策略/命名空间目标参与；`op_id`、`device_id`、
  `server_epoch` 不参与（否则“重试时带新 epoch”会变成 `OP_ID_REUSED`；epoch 由 410 单独回答）。
- **判定顺序**：`Root 可写性 → epoch → 命令形状 → 操作日志`。旧 epoch 与被暂停的 Root 在动任何状态前回答。
- **新错误码 `SERVICE_NOT_READY`**（503，`retryable=true`）：表示“本服务端这一版还没有装配该端点所需的执行
  链路”。不用 `NEEDS_RECOVERY` 借用语义（它专指“意图无法解释、需人工介入”）。**待与 design §15.4 同步**
  （本次未改 `docs/design.md`）。

## 5. 缺口（属 S052 服务端整合闭环，非本卡范围）

真实执行适配器尚未落地：`PutCommitStore`、`TargetPort`（put）、`NamespaceStore`（create/move）、`RemovalPort`（delete）、
`RestoreStore`/`ContentLeasePort`（restore）、`ConflictCommitStore`，以及 `begin_operation` → 执行 → `commit_operation`/
`reject_operation` 的接线。因此本卡每条命令的实际行为是：

| 命令 | 本版实际行为 |
| --- | --- |
| put/create/move/delete/restore（新 OpId） | 503 `SERVICE_NOT_READY`，不登记操作行、不追加事件批次、不碰工作目录 |
| 同一请求重试（已有记录） | 按记录回答 200/202/409（与是否有执行器无关，重试与响应丢失语义完整可用） |
| 结果查询 | 200/202/404，按记录回答 |

恢复条件：S052 把上述适配器接进 `apps/server::operations`，把“首次见到该键”的分支从 503 改成
`begin_operation` → 执行 → `commit_operation`/`reject_operation`。同时待办：`docs/design.md` §15.4 增加
`SERVICE_NOT_READY`（或改名后同步契约、核心映射表与 `interfaces.md`）。
