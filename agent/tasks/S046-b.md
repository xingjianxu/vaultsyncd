## 1. 交付内容

### 1.1 生成器扩展（`cargo xtask`，`format_version 4`）

一次改完同一处生成器，避免分两次：① `MediaType.schema` 改 `Option`；② 成功响应折叠成
`SuccessBody::{Json(name), Bytes}`，`Model::build` 只在 `Json` 时要求 schema 存在；③ `emit.rs` 对
`Bytes` 不生成解码器，TS 返回 `Uint8Array` 并走 `read_bytes`（非 2xx 仍按错误信封 `read_json`）；
④ 支持 `in: header`（`ApiOperation.header_params`、TS 签名参数 + `headers.set`）。

另外两个必要的边界（都由这次契约暴露出来，不是额外功能）：

- **同一端点可有多个 2xx**（200 整份 + 206 切片），但响应体形状必须一致，否则报错——否则“200 二进制
  + 206 二进制”这种真实契约无法表达。
- **请求头参数必须是运行时不管的头**：`accept`/`content-type`/`x-request-id` 由客户端自己写，声明成
  参数只会被静默覆盖，因此直接报错；可选请求头（`Range`）不生成参数，由调用方经 `init.headers` 传，
  生成器不为同一个头发明两种拼写。

### 1.2 契约（`api/openapi.yaml`）

- `finalizeUpload`：`POST /v1/roots/{root}/uploads/{upload}/finalize`，200 `FinalizedContent`，错误
  400/401/403/404/409/422/503/507，全部引用 `ErrorEnvelope`。
- `downloadVersionContent`：`GET /v1/roots/{root}/entries/{entry}/versions/{version}/content`，
  200/206 `application/octet-stream`（无 schema）与 400/401/403/410/503 错误信封。
- 新 schema：`FinalizedContent`（8 个必填字段）、`ObjectReuse`（`freshly_published`/`existing_verified`）。
- `putUploadPart` 的 `x-part-sha256` 声明成真实请求头参数（必填、`type: string`）。

### 1.3 HTTP 处理器（`apps/server/src/content.rs`）

两个路由都先 `principal_from` 再 `authorize_root`。适配器分别接：

- `FsAssembler`（`ContentPublisher`）：按块行把 `state_dir/uploads/…` 的块按序拼进对象区私有暂存副本
  （逐块核对长度、边写边算 SHA-256），再调 `objects::capture_object` 做“核对 → 不覆盖发布 → 发布后
  复核”，拼装用的工作副本无论成败都删除。
- `DbObjects`（`ContentObjectStore`）：`versions::record_object`，单事务并按 owner scope 校验。
- `DbVersionContent`（`VersionContentStore`）：`versions::current_version` 命中即用，否则在该条目
  `version_history` 里按身份找；找不到即 `VersionGone` → 410，绝不回退成当前 head 的内容。
- `DbLeases`（`ContentLeasePort`）：`object_leases` 的 `download` 租约（ttl 900 s），读取前建立、
  读完解除；解除失败只记录日志，不改判已读出的字节。
- `FsObjectPort`（`ObjectBlobPort`）：整份/区间读，短读是错误。

响应：整份 200 + `Content-Length` + `x-content-sha256` + `Accept-Ranges: bytes`；区间 206 +
`Content-Range: bytes start-end/total`；区间错误 400 `INVALID_REQUEST`；版本过期 410 `VERSION_GONE`。

## 4. 限制与后续

- **下载仍是“整段读进内存 + 切片”**：`read_object_range` 已按区间读，但单次响应最大到对象大小；
  流式分块响应留给下载端点卡（S046 §4 第 4 条仍成立）。
- **上传暂存不清理**：finalize 成功后 `upload_parts` 行与 `state_dir/uploads/<upload_id>/` 下的块文件
  都还在；拼装用的工作副本会删。过期会话清理与 finalize 后清理仍待后续卡（S046 §4 第 5 条）。
- **`FsObjectPort::stage_working_copy` 是校验复制**（不做 `FICLONE`，`fallback` 固定报告
  `unsupported`）：finalize 的拼装本身已经完整写过一遍字节，reflink 只省一次复制；生产优化随
  对象区适配器卡做。
- **`DbVersionContent` 的历史查询受 `MAX_VERSION_PAGE`（500）限制**：更早的版本按 410
  `VERSION_GONE` 回答。要彻底消除这个上限，需要在 `server-store` 暴露“按版本身份读一行”的查询
  （现有 `version_in_scope` 是私有 helper），本卡按指导用 `current_version`/`version_history` 未扩公共 API。
- **`INVALID_REQUEST`/`PART_CONFLICT` 仍待 design §15.4 补行**（S045 §1 起的已知缺口，需用户确认措辞）。
- 未使用 btrfs 测试卷（对象区与暂存都在临时目录）；未触碰 Windows 客体。
