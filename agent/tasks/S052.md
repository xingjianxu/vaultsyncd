## 1. 接口决定

契约摘要见 `docs/architecture/interfaces.md`「服务端提交执行器与观察运行时（S052）」。要点：

- **内容 put 有了真实执行链路**：`ExecutorContext::execute_put` = 读库定命名空间事实 →
  `begin_operation`（pending）→ `commit_put`（`fs_intents` 意图 → 经 `RootHandle` 观察/受控发布 →
  一个 `BEGIN IMMEDIATE` 里提交事件批次、版本、条目 revision、意图 `finalized`）→ 才 ACK。
  `ENOSPC`/`EDQUOT` → 507 `INSUFFICIENT_STORAGE`，其余存储故障 503；失败把操作记成稳定
  `rejected`，同一 OpId 不会“重试变成成功”。端点与执行器共用同一份 `request_digest`，
  响应丢失后的重试返回同一 `revision`/`root_seq`/`version_id`（结果里没有 root_seq 时用
  `operations.root_seq` 补齐）。
- **替换前提来自这次观察**：`TargetPort::publish` 只带 digest/size，因此 `WorkTreeTarget`
  在 `observe` 时记下实测身份并在 `publish` 用它作 `ExpectedTarget`；观察后被外部改写即拒绝，
  不改变端口契约。
- **外部采纳与后台观察**：`external::SqlExternalStore` 实现创建/更新/移动/可恢复删除（各自一个
  事务，保留历史、回收站与墓碑，不碰工作目录）；`ObserverRuntime` 周期为每个健康 Root 跑一轮
  `ExternalObserver::run_pass`，服务端自己的发布登记为自写意图（设备+inode+内容），不会被再采纳。
  运行时在独立线程 + current-thread runtime 上跑（端口不要求 `Send`），优雅停止先停观察再关库。
- **事件形状**（首个写入方就是 S052）：`events_json` 为对象数组，含 `kind`、`entry_id`、`path`、
  `revision`、可选 `version_id`/`hash`/`size`、`origin`（`client`/`external`），计数与摘要都是文本。
- **仍未装配**：create/move/delete/restore 的存储与工作目录适配器继续显式 `503 SERVICE_NOT_READY`
  （不写状态、不伪造成功）；inotify 后台接线未做（周期扫描已覆盖正确性，只影响时延）。

## 3. 验证（devShell，实际执行）

- `cargo test --locked -p vaultsyncd-server-tests --test http_loop -- --test-threads=1`
  （带 `VAULTSYNCD_S052_WORK_VOLUME`/`VAULTSYNCD_S052_STATE_VOLUME` 指向 `test-volume.sh create s052-work 192M`
  的卷内可写目录）→ **3 passed / 0 failed**，82.65 s：
  1. `full_http_loop_is_consistent_across_restart`：登录 → 注册 Root → 初始外部文件被观察循环采纳 →
     上传 3 块 → finalize → put **200 committed**（`revision`/`root_seq`/`version_id`）→ 同 OpId 重试
     **replayed=true 且三项相同** → 快照 version/hash/size 一致 → 固定版本下载逐字节等于上传内容 →
     外部改写后 `changes` 出现 `origin=external` 事件 → 真实优雅停止并用同一状态目录重启 →
     `changes` 批次（含 seq/events_json）逐字段相同、epoch 不变、版本/hash/revision 不变、下载仍是外部内容；
  2. `work_volume_full_never_reports_committed`：24 MiB 内容发布前把卷填满（大块数据 + 大量小文件，
     因为 reflink 的 CoW 也要元数据）→ put **非 200**（507/503）且 `state != committed`、工作文件仍是
     V1、条目 revision/版本不变；
  3. `state_volume_full_never_reports_committed`：把状态目录所在同一块小卷填满 → put 失败且
     `state != committed`；发布可能已发生（意图 `published`、重启可补完），因此只允许“工作文件是 V1 或
     已发布的新内容 + 意图证据”，并且操作记录**不是** committed。

## 4. 限制

1. **create/move/delete/restore 仍未执行**：端点继续 503 `SERVICE_NOT_READY`；它们的端口契约与 fake
   实现已在核心，但 SQLx/文件系统适配器与冲突副本、回收站恢复流程未接。
2. **inotify 未接入进程**：`ObserverRuntime` 用周期完整扫描（默认 1 s 间隔、1 s 稳定窗口）；
   溢出/权限/挂载故障的补扫路径已在 S050 的单元与真实目录测试覆盖，但“事件驱动 + 周期兜底”的组合
   尚未在进程级接线；本卡暂用周期扫描，不能宣称未知后续卡已承诺接线。
3. **自写意图只覆盖 put**：外部采纳自身不会产生自写；删除/移动的 `own_write` 登记要随对应执行器一起接。
4. **满盘场景是“整卷填满”**：准入要求状态目录与 Root 在同一 btrfs 文件系统（design §11.4），因此无法
   在测试里让“工作盘”与“状态盘”物理分离；两个用例分别以“数据空间先耗尽”和“整体空间耗尽”的方式
   触发，并各自断言不提前 committed。btrfs 删除大文件后空间回收有延迟（需事务提交/清理线程），
   所以用例不做“腾空后重试”的断言。
5. **重试语义的边界**：失败发生在 `begin_operation` 之前的存储故障（例如库整体不可写）时没有操作行，
   同一 OpId 之后可以真正执行；这是“没有记录就没有承诺”，不是把 pending 当 committed。
6. `WorkTreeTarget` 的暂存名来自 OpId（`put-<op>`），不使用请求里的 `staging_path`；发布端口自己生成
   `.vaultsyncd-stage.*` 名称，意图里记录的暂存名因此只作证据。
