## 1. 接口决定

- **Root 内串行化是核心规则，不是端口**：`commit::put::RootCommitGate` 用 `BTreeMap<RootId, serial>` 在进程内保证“同一 Root 同时只有一次提交”，第二个提交立即得到 `root_commit_busy`（不排队、不阻塞，避免请求堆在锁上）；不同 Root 互不影响。票据只能由 `acquire` 产生，`release` 因此不失败（不匹配即编程错误）。跨进程共享同一数据库的串行化需要数据库侧锁，属服务端组装卡，已在限制里写明。
- **基线复核五项、错误码分开**：epoch 不符 → `EPOCH_CHANGED`；条目 revision 不符 → `BASE_MISMATCH`；父目录或名称变化 → `SUBTREE_CHANGED`；条目不是普通文件 → `UNSUPPORTED_ENTRY`；工作目录现场指纹不符 → `RECONCILE_REQUIRED`。前四项都在动磁盘之前完成，只有现场指纹需要端口观察，因此“现场不同返回 RECONCILE_REQUIRED”成立而“过期 revision”仍得到客户端可重新规划的最精确码（I04）。
- **`PutFailure::error_code()` 是 wire 映射的唯一入口**：新增原因 `EpochChanged`/`BaseMismatch`/`SubtreeChanged`/`Reconcile`/`UnsupportedEntry`/`ObjectNotPersisted`/`ObjectSizeMismatch`/`Gate`/`Store`/`StoreContract` 各自给出稳定小写 `code()` 与（有对应 wire 码时）`domain::error::ErrorCode`；API 层不再写第二套字符串。
- **请求形状先于任何端口调用**：暂存名必须是单个文件名（I10），`target_path` 必须是 Root 内相对路径且**最后一段等于 `expected_name`**（“检查名称”和“发布到 target_path”必须是同一件事），`before` 里记录的条目/revision 必须与请求基线一致（一个请求里不能有两套基线）。
- **对象持久先于意图**：`PutCommitStore::object_state` 返回 `Missing` 或登记长度与请求内容不符时不写意图、不发布——没有固定成对象的内容没有可提交引用（design §11.2 步骤 3）。
- **元数据事务与意图收尾同一事务**：新增异步端口 `ports::put_store::PutCommitStore::{root_facts, entry_baseline, object_state, apply_put}`。`apply_put` 的契约是把“比较并写 `expected_revision` → `versions`/`entries.revision`/当前版本 → `changes` 批次 → 操作结果 → `fs_intents` `published → finalized`”放进一个数据库事务；返回 `PutRecord`。核心核对 `phase == finalized`、`digest`/`size` 等于请求内容、`revision` 严格推进；任何一条不符按 `store_contract_violation`（`NEEDS_RECOVERY`）停写，绝不 ACK。
- **顺序即验收**：`commit_put` = 请求形状 → Root 票据 → epoch → 基线 → 对象 → 现场 → `publish_put`（意图 → 发布 → published）→ `apply_put` → 核对证据 → ACK；无论成功失败退出前都释放 Root 票据。
- **现场复核两次但不宣称消除竞态**：CAS 预检查与 `publish_put` 发布前复核各观察一次现场；第二次不符（预检查后被外部写入）同样按 `RECONCILE_REQUIRED` 返回，且此时意图还没写。design §12.2 的“不保证保留每一次非协作瞬态写入”写进了模块文档。
- **未做**：`PutCommitStore` 与 `IntentLog` 的真实存储层适配（真实 SQLite 事务、`fs_intents` 收尾、`changes` 事件内容）；OpId 幂等与冲突条目（S036）；全 Root 启动恢复与强杀注入（S037）；create/move/delete（S038/S039）。

## 4. 限制

- **真实存储适配未落地**：`PutCommitStore` 只有测试假实现。真实 `apply_put` 需要接 `crates/server-store` 的 `entries`/`versions`/`changes`/`operations`/`intents`，并在同一 SQLx 事务里做 revision 比较并写与意图收尾；`IntentLog` 的 `fs_intents` 适配也未实现。在此之前 `apps/server` 没有可组装的提交存储，S036/S037 的幂等与恢复入口同样等待这层。
- **串行化只在单进程内**：`RootCommitGate` 是进程内的 `BTreeMap`，没有跨进程/跨连接协调；服务端只允许单进程拥有数据库时足够，若将来多进程共享需数据库侧锁。
- **拒绝语义是“立即失败”而非排队**：同 Root 并发提交得到 `root_commit_busy`（无 wire 码），调用方需自行退避重试；是否需要排队由调度器决定，属后续卡。
- **不保证外部瞬态写入**：两次现场观察之间仍可能被非协作程序改写，按 design §12.2 不承诺保留每一个瞬态版本；`publish` 端口自身的替换原子性与“检测到冲突停止替换”仍依赖适配器。
- **`expected_revision` 不校验“条目的当前内容版本等于 before 的摘要”**：现场摘要/身份已由 `TargetBefore.satisfied_by` 比对，但库里 `entries.content_version_id` 与本卡请求的一致性由存储层的 `apply_put` 契约负责，尚未在核心比对。
- **事件内容未定义**：`apply_put` 只约定“同一事务追加 changes 批次”，事件 DTO/schema 属协议与提交卡，本卡不规定 `events_json` 形状。
