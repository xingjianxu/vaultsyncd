## 1. 接口决定

- **判定与执行分开**：S034 的 `classify_put` 仍是唯一判定（前/后 hash 与现场比较）；本卡在 `recovery::startup` 只负责“按判定做事”。新增 `recover_root(log, target, store, at, root) -> Result<RecoveryReport, RecoveryError>`，逐条处理 `IntentLog::unfinished_puts` 的写入顺序。
- **四种可执行结果，卡住的一律不假装成功**：`Redone`（前 hash → 重做发布 + 补元数据事务）、`Completed`（后 hash → 只补元数据事务）、`Preserved`（第三种内容 → 保留前后两个可读版本、不覆盖不提交、等协调）、`NeedsRecovery`（读不到现场/已标 needs_recovery → 落盘 `needs_recovery` 并停写）、`Unresolved`（恢复动作失败：满盘、库忙、事务证据不符、缺条目基线 → Root 保持关闭，下次启动重试）。`is_committed()` 只对 `Redone`/`Completed` 为真。
- **一个补上的顺序缺口**：崩溃可能停在“发布完成、`published` 还没写”，此时现场是后 hash 而阶段仍是 `prepared`。恢复按现场证据先 `advance_put(published)` 再补事务（§11.3 第 4 行“校验目标与 desired_after 一致后完成同一操作”），否则 `apply_put` 会因阶段不是 `published` 被拒绝。集成测试的 `after_publish` 边界就是这个场景。
- **写入门只有“恢复过”才开**：`WriteAdmission` 新建时所有 Root 都是 `AwaitingRecovery`（默认拒绝），只有 `record(RecoveryReport)` 能把 Root 置为 `Open` 或 `Paused(report)`，没有“直接打开”的公开入口；`admit_write` 的拒绝码是 `recovery_pending` / `needs_recovery`。这就是“先恢复再开放写入口”的可断言实现，S041 的 readiness 只需读 `state(root)`。
- **只重放可证明的操作**：元数据事务的 `PutWrite{entry, expected_revision}` 只从 `expected_before` 快照取，`content` 只从 `desired_after` 取；`expected_before` 为 `Absent` 的意图（新建条目）没有条目身份可收尾 → `Unresolved{code: "missing_entry_baseline"}` 并保持 Root 关闭（create 恢复属 S038），不猜一个身份。
- **事务声称成功仍要核对证据**：`apply_put` 返回的 `phase` 不是 `finalized`、内容不等于 `desired_after`、revision 没推进，一律 `store_contract_violation` 停写（同 S035 的 `check_record` 判据）。
- **集成测试用文件型假端口，不新造生产适配器**：`tests/server-integration/`（包 `vaultsyncd-server-tests`，design §5.8 指定的位置）用 `state/` 追加日志 + `work/` 真实文件实现三个端口；工作文件用真实 inode 与 rename 替换，因此“发布换了新 inode”“前快照的 inode 比较”是真的。摘要由内容确定性派生（不是 SHA-256，假端口不需要对象层）。
- **强杀是外部 SIGKILL，不是自我退出**：子进程（`src/bin/crash-child.rs`）在每个边界把边界名刷盘到 `state/boundary.txt` 后挂起，父进程读到后 `kill()`（SIGKILL，断言 signal 9），再回收子进程；父进程随后用同一份磁盘证据跑恢复，因此“重启”没有任何内存残留。
- **未做**：真实 `IntentLog`/`PutCommitStore` 适配与 `apps/server` 组装（S041）；create/move/delete 意图接入同一条启动顺序（S038/S039）；`pending` 操作记录的收尾（需要 `conflicts`/`operations` 真实表，S036 限制仍在）；跨进程互斥。

## 3. 验证（devShell `nix develop --command bash -c '…'`，实际执行）

- `cargo test --locked -p vaultsyncd-server-core` → 0，**79 passed / 0 failed**（S036 的 66 项全部仍通过，新增 13 项）。关键断言：
  - **先恢复再开放写入**：新建门直接 `recovery_pending`；报告 `pauses_writes` 时只能是 `Paused`（`needs_recovery`）且保留报告；干净报告才 `Open`；逐 Root 独立。
  - **未发布 → 重做**：`prepared` + 前 hash → 发布一次目标内容、记 `published`、补事务，得到 `Redone`；重做失败（`ENOSPC`）→ `Unresolved{no_space}`、阶段仍 `prepared`、不写事务。
  - **已发布 → 只补事务**：`prepared` 与 `published` 两种阶段 + 后 hash → `Completed`，**不再发布一次**；`prepared` + 后 hash 会先补记 `published`。
  - **外部改写 → 保留双方**：第三种内容 → `Preserved{published_target_changed}`，不发布、不提交、意图保留为证据，报告里同时给出前/后候选摘要。
  - **无法解释 → NEEDS_RECOVERY**：目标不可读 → 意图落盘 `needs_recovery`、停写、不发布；已标 `needs_recovery` 的意图不再自动收尾。
  - **无假成功**：库失败（`SQLITE_BUSY`/`RevisionChanged`）与“事务声称成功但内容不符” → `Unresolved`，`committed_versions()` 为空；`expected_before = Absent` → `missing_entry_baseline` 且不猜身份；意图日志读不出 → `RecoveryError::Intent` 且门保持 `recovery_pending`。

## 4. 限制

- **真实存储未落地**：恢复依赖 `IntentLog`/`PutCommitStore`/`TargetPort`，三者仍只有假实现；`apply_put` 的“同一事务写版本/条目/changes/结果并把意图收尾”要靠 `crates/server-store` 的真实 SQLx 适配，崩溃语义才能在生产上成立。集成测试证明的是**核心编排 + 端口契约**，不是真实 SQLite 事务。
- **新建条目（`expected_before = Absent`）无法收尾**：put 意图里没有条目身份，恢复只能 `Unresolved{missing_entry_baseline}` 并保持 Root 关闭；S038 的 create/move/delete 意图接入后需要按 `fs_intents` 的命名空间证据扩展。
- **`Preserved` 不阻塞 Root**：可解释的外部改写只让该条目等协调（`needs_reconciliation()`），Root 仍开放；协调/采集路径（S031 的 planner 与后续采集卡）尚未接入，因此该意图会一直留在未完成清单里。
- **`pending` 操作记录不收尾**：S036 的 `operations` pending 行仍只能返回 `operation_pending`（`NEEDS_RECOVERY`），本卡未接 `ConflictCommitStore`（真实 `conflicts` 表不存在）。
- **写入门只在本进程内**：跨进程（第二个服务进程未恢复就写）靠部署约定与数据库约束，属 S041/组装卡。
- **强杀是 SIGKILL，不覆盖断电/掉电**：`fsync` 顺序语义由端口契约保证，装置用 `sync_all` 近似；T23 的“每个持久化边界”按当前 put 提交路径的九个边界覆盖，`objects` 的 fsync 边界属对象存储卡（S013/S033）。
- **装置摘要不是 SHA-256**：假端口用内容确定性派生的 32 字节，只为区分前后内容；不改对象层。
