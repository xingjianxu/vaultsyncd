## 1. 接口决定

- **规则与 I/O 分层**（design §5.5）：卡里写的落点 `crates/server-core/src/api/roots.rs` 落实为**纯规则**——`AllowedBases`（允许基目录）、`CandidateFacts`（平台探测结论）、`evaluate_registration` 与 `RegistrationRejection`（设计错误码/HTTP 码/`details.reason`）。挂载判定沿用 S013 的 `mounts::admission::evaluate`，不在核心重写一份；HTTP 与平台探测的装配放在 `apps/server/src/roots.rs`。为此 `apps/server` 新增依赖 `vaultsyncd-platform-linux-server`（服务端本就在 Linux 上构建，且该 crate 不进 `default-members`，便携检查不受影响）。
- **允许基目录按分量判、不折叠路径**：`/data/root` 不是 `/data/rootx` 的祖先；相对路径与含 `..` 的路径一律不在允许范围内（`Path::components()` 会折叠 `.`，因此“规范化形式”这条只对 `..` 生效，注释已写明）。基目录配置非法（空集合、相对、含 `..`）直接 `config_invalid_value`，不把空集合解释成“不限制”。
- **两段检查**：先用客户端给的文本判（越界立刻 403，**连探测都不做**，否则这个接口就是任意路径存在性探针），探测后再按规范路径判一次（符号链接不能把 Root 带出允许范围）。
- **错误码只从设计闭集里选**：越界/未配置基目录是授权问题 → 403 `ACCESS_DENIED`（`details.reason=outside_allowed_bases`，不回显允许目录）；其余配置阶段拒绝（不是目录、FUSE/非 btrfs/NOCOW/嵌套子卷/内部目录重叠/已注册父子或别名重叠、扫描不完整）→ 422 `UNSUPPORTED_STORAGE_BACKEND`（design §11.4 明确“配置阶段拒绝返回该码”）。扫描不完整**不是通过**，核心单列为 `Inconclusive`。
- **注册不改写目录内容**：只用 `RootHandle::open`（O_DIRECTORY|O_NOFOLLOW + 句柄身份核对）与 `scan_root` 做只读探测，然后写 `roots` 行与合成根条目。既有文件不导入、不清空、不改名；启动流程也不扫描 Root 内容（不存在“以空库覆盖既有文件”的路径）。
- **`pending_import` 现在是常量 `true`**：注册确实不导入既有内容，初始采集属 S049，因此该字段对每个新注册 Root 都为真。**没有加 `roots` 迁移**：把“待导入 → 已导入”推进的时机由采集卡一次决定更安全（SQLite 改 CHECK 要重建 `roots`，而它被多张表外键引用）。这是本卡唯一有意留下的“常量字段”。
- **管理权限**：首发只有一位 owner（`vaultsyncd-admin init` 只建一个账号，没有账号注册接口，design §7.2 的 `users` 也没有角色列），因此“仅 owner 管理”落实为“必须有有效会话”；多角色区分需要账号卡先加角色列，本卡不虚构一个角色列。
- **普通客户端看不到绝对路径**：`GET /v1/roots` 只返回 `root_id` + `health`，并按 `root_id` 排序（库里的 `ORDER BY absolute_path` 只服务运维，避免清单顺序泄露路径相对位置）；注册响应同样不回显路径。
- **契约新增 5 个 schema + 2 个端点**（`GET /v1/roots`、`POST /v1/admin/roots`）：`RootHealth`、`RootSummary`、`RootList`、`RootRegisterRequest`、`RootRegistered`；用 `cargo xtask generate` 重新生成 Rust DTO 与 TS 客户端，未手改生成代码。

## 4. 限制

1. **没有真实 btrfs 卷上的“合规目录注册成功”验收**：本轮的接受路径只有核心规则单测（`Accepted` 分支）与端点用例的拒绝路径；endpoint 级成功注册需要 btrfs 工作目录与 btrfs 上的状态目录，本卡时间窗口内没有跑 `tests/platform/linux/` 的 loop 卷脚本。admission 层（后端/NOCOW/嵌套挂载/内部目录/已注册别名与父子重叠）的实卷证据已有 S013 的 60 项脚本，但**经 HTTP 端点的完整成功注册尚未实测**。恢复条件：在 btrfs loop 卷上建 `[roots].allowed_bases`，用一个临时状态目录跑 `POST /v1/admin/roots`，并核对样本哈希不变——本卡未做，不能宣称已验收。
2. **FUSE 拒绝只有准入层证据**：端点用例用的是“普通文件”这一确定性的 `NotADirectory` 分支；FUSE 挂载在测试环境不可得，FUSE 判定由 `mounts::admission`（S013）覆盖。
3. **`pending_import` 是常量**：没有持久化列，重启后 `GET /v1/roots` 也读不回“待导入”。采集卡（S049）需要一次迁移把状态落库。
4. **健康状态只在注册时写入**：运行期挂载漂移复核（`RootSnapshot::compare` → `ROOT_UNAVAILABLE` 暂停 Root、不推导删除）尚未接到后台巡检；`GET /v1/roots` 报的是数据库里的 `health`，不是当场复核结果。
5. **`epoch` 写 `ServerEpoch::ZERO`**：进程还没有独立的 epoch 来源（`GET /v1/capabilities` 未实现），注册不发明第二个来源。
6. **多账号角色**：admin 端点只要求有效会话；真正的 owner/成员区分需要账号卡加角色列。
7. **探测在 `spawn_blocking` 里做但按 Root 串行**：注册是低频管理动作，未做并发控制；并发注册同名路径仍可能撞唯一索引（映射为 503，不会写坏数据）。
8. **TS 产物未类型检查**：生成器写了 `types.ts`/`client.ts`，worktree 内无 `node_modules`，未跑 `pnpm typecheck`。
