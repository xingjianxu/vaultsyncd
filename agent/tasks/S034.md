## 1. 接口决定

- **阶段与编码放核心，表与事务放存储层**：`commit::intent::PutPhase` 固定 `prepared/published/finalized/needs_recovery` 与允许的转换；`fs_intents` 只存同一套文本。S029 明确把 `expected_before`/`desired_after` 的**编码**留给本卡，因此 `TargetBefore`/`TargetAfter` 的 `to_json`/`from_json` 是唯一编解码实现：键顺序固定，计数与字节写成十进制字符串（与 domain 的 `to_decimal` 惯例一致，避免 JSON number 丢精度），`present` 是布尔；解码器故意收窄——未知键、缺字段、类型不符、`null`、数字、转义与非 object 顶层全部报 `StateJsonError`，不猜现场。
- **两个新端口，都只报事实**：`TargetPort::observe/publish` 把“确认不存在”与“读不到”分开（`TargetObservation::Absent` vs `TargetError::Unreadable`），发布后必须回报实测身份与 SHA-256；`IntentLog` 是异步端口（`begin_put/advance_put/load_put/unfinished_puts`），用 `async fn` + 泛型而非 dyn 对象，以直接对接 S029 的异步 SQLx 事务。真实实现（`fs_intents` 适配）属 S035；本卡只提供契约与假实现。
- **顺序即不变量**：`publish_put` = 现场复核（前提不符返回 `before_mismatch`，不写意图、不动磁盘）→ 写 prepared 意图（失败即返回，不发布）→ 发布 → 发布后复核实测摘要与字节数（不符不推进阶段）→ 记 `published`。`finalize_put` 单独暴露，供 S035 在写 entries/versions/changes 的同一事务内调用；未发布就收尾被阶段规则拒绝。
- **错误永远不是 committed**：`PutFailure { reason, intent_id, phase }`，`is_committed()` 恒 `false`，已写入的意图行既不删除也不回退（它就是要给恢复读的证据）。编排函数返回 `Box<PutFailure>`：`PutFailure` 含 `TargetBefore` 快照，直接返回会触发 `clippy::result_large_err`。
- **恢复只读证据**：`recovery::classify_put` 把 §11.3 的四行映射成 `Redo`（prepared 且现场满足前提）、`Complete`（现场已是目标内容）、`Reconcile`（第三种现场，分 prepared 被改 / 发布后被改 / 发布被回退，保留双方不覆盖）、`NeedsRecovery`（读不到现场或已被标 `needs_recovery`，`pauses_writes()` 为真）；`plan_root` 保持写入顺序，任一意图不可证明即 `pauses_writes = true`。
- **依赖**：`server-core` 新增 `vaultsyncd-domain`（身份与时间戳的唯一来源，与 S026 对 server-store 的同一规则）；`tokio` 只在 dev-dependencies 驱动异步测试。`server-store` 只在 **dev-dependencies** 接 `server-core`，用于证明编码穿过真实 `fs_intents`；生产依赖方向仍为“适配器实现核心端口”。
- **未做**：基线 revision/epoch/父目录与名称的现场复核、控制锁与元数据事务（S035）；OpId 幂等与冲突条目（S036）；全 Root 启动顺序、强杀注入与恢复报告（S037）；create/move/delete 与可恢复删除（S038/S039）；`TargetPort` 的真实 Linux 适配（S035，`files::publish` 已存在）。

## 3. 验证（devShell `nix develop --command bash -c '…'`，实际执行）

- `cargo test --locked -p vaultsyncd-server-core` → 0，**28 passed**（原有对象用例 12 + 新增 16）。关键断言：
  - happy path 的跨端口调用顺序为 `target observe` → `intent begin prepared` → `target publish` → `intent advance published`，`finalize_put` 后 `phase = finalized`；
  - 前提不符 → `before_mismatch`，未写意图、未发布；目标不可读 → `target_unreadable`，不把故障当成“不存在”；
  - 写意图失败（`SQLITE_BUSY`）→ `intent_storage_failed` 且从不发布；发布满盘 → `no_space`、`phase = prepared`、`is_committed() = false`、意图行仍在；
  - 端口名义成功但实测 3 字节（短写）→ `published_target_mismatch`，阶段停在 `prepared`；
  - 未发布就 `finalize_put` → `illegal_intent_transition`，意图仍 `prepared`；
  - 覆盖场景：前提 `Present(snapshot)` 与现场一致时发布意图目标内容；证据 JSON 往返与拒绝矩阵（非 object、尾随内容、`null`、JSON number、未知键、类型错、非十六进制 entry、负 revision、`after` 不能为 `present:false`）。
  - 恢复判定：prepared+前提 → `redo`；prepared/published+目标内容 → `complete`；第三种现场 → 三个 `Reconcile` 原因；不可读/已标 `needs_recovery` → `needs_recovery` 且 `pauses_writes`；`finalized` → `already_finished`；`plan_root` 保持写入顺序、任一条不可读即暂停写入。

## 4. 限制

- **真实端口尚未组装**：`TargetPort` 与 `IntentLog` 目前只有测试假实现；`fs_intents` 适配与 `files::publish` 的真实包装属 S035，本卡的顺序与证据规则靠假端口验证，不构成平台验收。
- **现场复核是单文件最小集合**：只比较 entry/revision/摘要/长度/文件身份是否与 `expected_before` 一致；epoch、控制锁、父目录与名称的完整 CAS、`RECONCILE_REQUIRED` 响应属 S035。
- **`Complete` 尚未执行**：恢复给出结论但不写库、不动磁盘；把 `complete` 落成一次事务、崩溃注入与 `NEEDS_RECOVERY` 的持久标记属 S037。
- **时间戳不校验单调**：`publish_put` 用同一个 `at` 写 prepared 与 published，单调性由存储层（S029 的 `TimeWentBackwards`）判定，核心不再重复。
- **`needs_recovery` 只能由恢复流程置入**：本卡没有“进入 needs_recovery”的写入路径（S037 落地），只有判定与转换规则。
