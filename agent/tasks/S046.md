## 1. 接口决定

全部落在 `crates/server-core/src/api/content.rs`（新增）与两个新端口模块，遵循“核心定规则、适配器
报事实”：核心不碰 HTTP、不碰文件系统、不读时钟。

- **finalize 顺序固定**：读会话 → 读块行 → 核对收齐（块数、索引连续、每块长度等于几何）→
  `open` 时先标 `complete` → 拼装并发布对象 → 核对总长度与总 SHA-256 → 登记内容对象 → 标
  `finalized`。任一步失败都不返回内容引用。
- **finalize 不提交条目**：不写 `entries`/`versions`/`changes`/`operations`；返回
  `ContentReference { digest, size, storage_path }`。条目 head 由后续 put/create 按 CAS 提交
  （design §15.2「不修改条目 head」，I01：finalize 成功 ≠ 同步完成）。单测
  `finalize_publishes_content_and_only_returns_a_reference` 断言调用序列只有
  `load → parts → complete → finalized` 加一次对象登记。
- **块不齐 → `ContentFailure::IncompleteUpload { expected, present }`**，不改任何状态、不拼装。
  HTTP 层建议映射 400 `INVALID_REQUEST`（错误码闭集里没有更贴切的；design §15.4 的前置条件类错误）。
- **拼装内容与快照不符 → `ContentFailure::ContentMismatch`，并且放弃会话（`abort`）**：校验失败
  不安装、不提交；已发布但不符的对象不登记（design §13.2、I05）。
- **重放幂等**：已 `finalized` 的会话再 finalize 直接返回同一引用（`replayed = true`），不重新发布、
  不改状态；`aborted` 会话返回 `Upload(PartsClosed)`。
- **下载按版本取字节**：`VersionContentStore` 只回答 `(root, entry, version) → {digest, size}`；
  适配器把“版本不存在/已过期清理”映射成 `VersionContentError::VersionGone`，核心转
  `ContentFailure::VersionGone`（410 `VERSION_GONE`）。核心还会拒绝“适配器返回的版本/条目与请求
  不符”的事实（不拿另一个版本的字节冒充）。单测
  `download_uses_the_requested_version_even_after_head_moved` 用“版本事实仍是旧内容、路径上的
  current 已换成新内容”的假存储断言读取路径来自版本的内容地址。
- **Range 收敛**：`bytes=start-end`、`bytes=start-`、`bytes=-suffix`；终点超出对象长度收敛到最后
  一个字节，后缀长于对象等于整份内容；多区间、非 `bytes=`、反向区间、规范十进制以外一律
  `InvalidRange`；起点越界、`-0`、空对象上的任何区间为 `RangeNotSatisfiable`。部分切片无法在
  服务端核对整份摘要（design §13.2 的整文件校验在客户端），整份读取则核对 SHA-256。
- **下载租约防 GC**：`open_download` 在读取之前 `acquire` 一条 `Download` 用途租约，读完调用
  `finish_download` 解除；租约失败不读字节，解除失败只报告而**不**改判已读出的字节（design §7.2、
  §11、§19.4）。单测断言 `lease acquire` 发生在 `read_object_range` 之前，且读过期版本时不建租约。
- **端口变化**（都是纯增量，已有实现同步跟进）：
  - `UploadSessionStore` 新增 `parts`/`mark_complete`/`mark_finalized`/`abort`；
    `apps/server/src/uploads.rs` 的 `DbUploads` 走 `server-store` 的
    `parts_of`/`mark_upload_complete`/`mark_upload_finalized`/`abort_upload`（各自独立事务）。
  - 新 `ports/content_publish.rs`：`ContentPublisher::publish_parts`（拼装 + 不覆盖发布，返回实测
    字节数/摘要/对象区相对路径）、`ContentObjectStore::record_published`（登记 `objects`，幂等）；
    `PublishFailure` 带 `no_space` 标记供 507 映射。
  - 新 `ports/version_content.rs`：`VersionContentStore::version_content`。
  - `ObjectBlobPort` 新增 `read_object_range(object, offset, length)`（`StoredSlice`）：短读为错误，
    不补零；`objects/capture.rs` 测试假端口与 `platform-linux-server/examples/object-capture.rs`
    的实现已跟进（后者用 seek + `take`）。

## 4. 限制与阻塞

1. **已由 S046-b 补齐**：`api/openapi.yaml` 现含 `finalizeUpload`（JSON，`FinalizedContent`）与
   `downloadVersionContent`（200/206 二进制切片 + 400/401/403/410/503），生成器随之支持二进制响应与
   `in: header` 参数（`format_version 4`），`cargo xtask generate --check` 无 diff。落地步骤（原记于此，
   已全部执行）如下：
   - 下载响应是二进制切片（200/206 + `Content-Range`），而生成器 `MediaType.schema` 是必填、
     `build_operation` 要求每个响应都有 `application/json` 具名 schema，因此“声明即生成失败”。
   - 落地步骤：① `MediaType.schema` 改 `Option`；② `ApiOperation.success_type: String` 换成
     `SuccessBody::{Json(name), Bytes}`，`Model::build` 只在 `Json` 时校验 schema 存在；③
     `emit.rs` 对 `Bytes` 不生成 decoder、TS 返回 `Uint8Array` 并用 `read_bytes`（`response.ok` 为假
     时仍走 `read_json` 错误信封）；④ 契约补 `finalizeUpload`（JSON，`FinalizedContent` schema）、
     下载端点（二进制 2xx + 410 `VERSION_GONE` + 400 `INVALID_REQUEST`）；⑤ `cargo xtask generate`、
     `cargo xtask generate --check`、`cargo test -p vaultsyncd-xtask`，并在有 `node_modules` 的环境
     补 `pnpm --recursive run typecheck`。预计 30—40 分钟。
   - 与 S045-b §4 第一条（`x-part-sha256` 未进契约）是同一处生成器扩展，建议合并成一张契约/生成器
     卡一起做，避免两次改生成器。
2. **已由 S046-b 补齐**：`apps/server::content` 挂上两个路由（在 `Principal`/`authorize_root` 之后），
   适配器分别是 `FsAssembler`（块拼装 + `objects::capture_object` 的发布语义）、`DbObjects`
   （`versions::record_object`）、`DbVersionContent`（`versions::current_version` +
   `versions::version_history` 按身份查）、`DbLeases`（download 租约）与 `FsObjectPort`（对象区
   整份/区间读）；`apps/server/tests/content.rs` 有 9 条 HTTP 级用例。
3. **`ContentFailure` 未实现 `PartialEq`**（含 `ContentLeaseError`，后者是带文本的错误）：测试用
   `matches!` 断言。若后续需要更细的相等比较，应给端口错误加结构化字段而不是给核心失败加派生。
4. **下载读取仍是“整段读进内存 + 切片”**：`read_object_range` 已按区间读，但 HTTP 层若直接复用
   会把切片一次性读进内存（单次 ≤ 对象长度）；流式分块响应留给下载端点卡。
5. **未做**：上传会话过期清理、finalize 后的暂存块清理（`upload_parts` 行与 `state_dir/uploads`
   下的文件）、每 Root 并发 finalize 上限。
