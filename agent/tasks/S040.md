## 1. 接口决定

- **落地位置按卡面**：新增 `crates/server-core/src/history/`（`version`、`trash`、`mod` 的失败词汇），
  端口在 `ports/restore_store.rs` 与 `ports/content_lease.rs`。本卡不写 SQLx 适配器，与 S035/S039 的
  “核心 + 端口契约先落地、真实适配归装配卡”一致。
- **历史版本恢复 = 新版本，不是回滚（I12）**：事务输入 `VersionRestoreWrite` 只带 `restored_from`
  （旧版本身份）与旧版本内容（同一内容对象），没有“改旧版本”的字段；`apply_version_restore` 契约要求
  追加新版本行、按比较并写推进条目 revision/当前内容、写事件批次与操作结果并把意图收尾。核心在 ACK 前
  核对 `result.version != request.version`、`result.content == 旧版本内容`、`revision > 基线`，不满足即
  `store_contract_violation`（wire `NEEDS_RECOVERY`）停写人工核对。
- **内容租约保护“核对 → 引用”的窗口**：`ContentLeasePort::acquire` 在发布之前建立（恢复历史版用
  `commit` 用途、恢复回收站文件用 `download` 用途，与 `object_leases.purpose` 同一套取值），到期时间
  `at + RESTORE_LEASE_TTL_SECONDS(900)`。租约失败 → 不写意图、不发布（避免 GC 在中间回收对象后发布
  空内容）。提交成功后解除；解除失败只记 `RestoreFailure::lease_expires_at`，不改判已提交结果，也不
  假装解除。
- **提交协调全部复用 put**：`RootCommitGate`（同 Root 串行）、epoch/revision/父目录名称复核、
  `publish_put`（prepared → published + 发布后复核）、单一元数据事务、失败保留意图。恢复没有第二套
  状态机。
- **幂等（I06）先于基线判定**：`operation(key)` 在版本/清单事实之前查。同摘要 → 重放首次结果（不再建
  租约、不再写事务、不再发布）；不同摘要 → `op_id_reused`；已登记但无结果 → `operation_pending`
  （wire `NEEDS_RECOVERY`），不重做。
- **回收站恢复不覆盖现有内容（T13）**：`name_occupant` 只把活跃条目算占用（软删除的条目本身不算），
  被占用时同父目录另名 `名称（恢复）`、`名称（恢复 2）`…（扩展名保留，`.gitignore` 整段算原干），
  最多 `MAX_RESTORE_NAME_ATTEMPTS = 32` 次，仍失败 → `restore_name_unavailable`；发布前现场必须空缺
  （`TargetBefore::Absent`），事务内再核一次占用（`NameOccupied`）。实际名称与路径随结果返回。
- **清单是唯一事实**：清单不在 → `restore_not_in_trash`；保留期已过 → `version_gone`（wire
  `VERSION_GONE`）；清单 revision 与请求不符 → `base_mismatch`；原父目录不存在或不是目录 →
  `subtree_changed`（不把子树悄悄丢到别处）。
- **失败词汇**：`RestoreFailure` = `reason` + 稳定码 + `error_code()`（design §15.4 里已存在的码，
  没有对应码的返回 `None` 交 API 决定）+ `intent_id`/`phase` 证据 + `lease_expires_at`；
  `is_committed()` 恒 `false`。

## 3. 验证（devShell `nix develop --command bash -c '…'`，实际执行）

- `cargo test --locked -p vaultsyncd-server-core --lib` → 0，**143 passed / 0 failed**（S039 的 122 项
  全部仍通过，新增 21 项）。关键断言：
  - **恢复创建新当前版本（I12）**：`result.version != request.version`、`restored_from == 请求版本`、
    `content == 旧版本内容（digest 0x22 / 5 字节）`、`revision 8 > 基线 7`；轨迹顺序是
    `lease acquire` → `target observe` → `intent begin prepared` → `target publish` →
    `intent advance published` → `store apply_version_restore` → `lease release`；租约用途 `commit`、
    到期 `at + 900`。
  - **重放稳定（I06）**：同 `OpId` 同摘要第二次恢复返回同一结果，`writes` 仍为 1、`leases.acquired` 仍
    为 1（不重复事务、不重复建租约）；同 `OpId` 不同摘要 → `op_id_reused`（wire `OP_ID_REUSED`）；
    预置 pending 记录 → `operation_pending`（wire `NEEDS_RECOVERY`）且无事务。
  - **历史过期**：`retained_until < at` → `version_gone`（wire `VERSION_GONE`），不建租约、不写事务。
  - **基线与形状**：条目 revision 已前进 → `base_mismatch`；目录条目 → `unsupported_entry`；目标路径
    名称与条目名称不符 → 请求形状拒绝；现场与指纹不符（目标已不存在）→ `reconcile_required` 且不写意图。
  - **租约与发布失败**：租约 `object_not_registered` → 不写意图、不发布；发布失败 → `is_committed()==false`
    且租约被解除、无事务。
  - **证据不一致停写**：适配器把旧版本本身当成新版本 → `store_contract_violation`（wire
    `NEEDS_RECOVERY`），`phase == published` 作为证据。
  - **回收站文件恢复**：发布目标就是原路径 `docs/report.docx`，内容是清单里的版本（digest 0x0d / 11
    字节），租约用途 `download` 并解除；事务里 `intents == [请求意图]`、条目身份不变、
    `expected_revision == 7`。
  - **目标占用另名（T13）**：原名称被活跃条目占用 → 实际名称 `report（恢复）.docx`、路径
    `docs/report（恢复）.docx`、`renamed == true`；发布目标与事务路径都是新路径，**没有任何调用指向原
    路径**；`alternate_name` 单测覆盖 `（恢复）`/`（恢复 2）`/`.gitignore`/无扩展名。
  - **目录恢复**：`namespace mkdir docs/report.docx` 被调用，发布与意图都为空；清单多于一行 →
    `restore_subtree_unsupported`（wire `UNSUPPORTED_ENTRY`），不发布、不写事务。
  - **清单类拒绝**：清单不存在 → `restore_not_in_trash`；保留期已过 → `version_gone`；清单 revision
    不符 → `base_mismatch`；原父目录不存在 → `subtree_changed`；同 `OpId` 重放 → 同一结果、单次发布。

## 4. 限制

- **带后代的目录子树恢复未接入**：清单多于一行时返回 `restore_subtree_unsupported`（明确失败、不做部分
  恢复）。缺的是批量编排：按路径深度 `mkdir`、逐文件“租约 + 意图 + 发布”、多意图在单一事务里一起收尾
  （`TrashRestoreWrite::intents` 已按多意图设计，`TrashRestorePorts` 已带 `namespace`，只差循环与逐文件
  暂存名派生规则）。恢复条件：另立一张卡（或并入装配卡），用真实存储 + 假端口证明“三文件两目录”的
  顺序与失败回滚。**这是本卡与卡面“目录清单恢复”的差距，不能算已完成。**
- **真实适配器仍未落地**：`RestoreStore`/`TrashRestoreStore`/`ContentLeasePort` 的 SQLx 实现与进程内装配
  未写，因此“旧版本哈希在真实 SQLite 里不变”目前由端口契约 + 核心证据核对保证，没有真实库用例
  （S039 在存储层证明过删除不动历史；恢复侧的库用例应在适配卡补）。恢复的 wire 端点（`POST /operations`
  的 Restore 命令、`GET .../versions`）同样属装配/端点卡。
- **另名规则不截断**：另名按固定后缀追加，不做名称预算截断（design §10.2 的冲突名有预算逻辑，恢复名
  暂未复用）；超长名称会让 `validate_name` 失败并逐个跳过，最坏落到 `restore_name_unavailable`。
- **暂存名由客户端给**：文件恢复用请求里的 `staging_path`（与 put 一致）；带后代批量恢复后需要由服务端
  派生每文件暂存名，随第 1 条一起做。
- **回收站恢复不做内容回收**：清单行的删除在事务里完成，但“过期后回收对象/压缩墓碑”仍属同步协议与 GC 卡。
